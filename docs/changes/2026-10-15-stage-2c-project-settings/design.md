# 2C 설계안 — 프로젝트 설정·IA·기본 양식

상태: 2026-10-15 사용자 추천안 승인. 사용자는 “설계안은 추천안대로 승인합니다. 새 폴더 3곳 생성과 문서 푸시도 허용합니다. 공통 변경 요청을 조율 채팅에 전달하고, 필요한 계약이 준비되면 2C 구현을 진행해주세요.”라고 지시했다. 아래 제안 표현은 검토 당시 문맥을 보존한다. 6절의 새 소스 폴더 세 곳과 추천 범위는 승인되었으며 공통 계약 준비 후 구현한다. 공통 파일 소유권·PR/병합/배포 경계는 유지한다.

기준: `codex/stage-2c-project-settings`, `4cfd066574ca97241372d3b56561fb96f0430847`. 담당 경계는 [2단계 인계](../2026-10-15-staged-development/stage-2.md), 제품 계약은 [제품 정의](../../product.md)와 [1단계 설계 4~6절](../2026-10-15-stage-1-foundation/design.md)을 따른다.

## 1. 결과와 범위

프로젝트의 IA를 사람이 등록·수정하고, 앞으로 만드는 시트의 기본 열과 표시 설정을 편집한다.

| 구분 | 이번 설계의 범위 | 완료 조건 |
| --- | --- | --- |
| 프로젝트 정보 | 기존 조회·수정 API를 이용한 이름·설명 편집 제안 | 이름 검증·revision 충돌 처리, 입력 보존 |
| IA | 목록·추가·수정·상위 항목 변경·순서 변경·삭제 | 프로젝트 내 화면 ID 유일성, 순환·프로젝트 간 연결·참조 중 삭제 차단 |
| 기본 양식 | 시스템 열 이름·순서·너비, 텍스트 사용자 열 추가·수정·삭제 | 열과 표시 설정을 함께 저장하고 새 시트만 변경된 양식 사용 |
| 웹 | 프로젝트 설정 화면과 저장·오류·충돌 처리 | 실제 브라우저에서 한글 입력·키보드·저장·재조회 확인 |

XLSX·CSV 입력과 AI 분석·검토·등록 연결은 3B 공통 AI 계약 이후다. 파일 형식 확장, 시트 편집·생성 구현, 플로우·후보 모델, 공유·인증·배포는 이번 구현에 포함하지 않는다. 2B와의 양식 복사·IA 참조 통합 검증은 포함한다.

## 2. 확정 계약과 현재 구현의 차이

확정된 요구:

- IA의 내부 UUID와 업무용 화면 ID, Figma node ID는 별개다. 화면 ID는 trim 후 프로젝트 내에서 유일하며 대소문자를 구분한다. 화면 ID를 바꿔도 기존 UUID 연결은 유지한다.
- 상위 IA 항목은 같은 프로젝트에 속해야 하고 순환할 수 없다. 참조 중인 항목은 연결을 해제한 뒤 삭제한다.
- 기본 양식은 프로젝트당 하나다. 새 시트에 사본을 만들고 기존 시트는 양식 변경을 따라가지 않는다.
- 시스템 필드 8개는 각각 한 번씩 존재한다. 시스템 열 삭제는 제외하고 사용자 열은 텍스트로 한정한다. 표시 이름·위치로 값을 식별하지 않는다.
- 수정은 기대 revision이 맞을 때만 저장한다. 서버 재조회가 미저장 초안을 덮어쓰면 안 된다.

설계 기준 커밋 `4cfd066`에서 확인한 상태(구현 결과는 change.md 참조):

- DB에는 `projects`, `files`만 있다. IA·양식 응답 DTO와 업무 HTTP 경로는 없다.
- `CreateIaItemDto`는 `screenId`, `name`, `position`과 선택적 `description`, `parentId`를 받는다. `UpdateIaItemDto`는 이를 상속하므로 PATCH에서도 세 필드가 모두 필수다.
- `UpdateTemplateDto`는 `expectedRevision`, `columns`, `view` 전체를 받는다. 열 UUID 중복·시스템 필드 완전성·표시 열 일치를 검증한다.
- 케이스의 `screenIds`는 이름과 달리 IA 내부 UUID 배열이다. 이 필드에 업무용 화면 ID 문자열을 넣지 않는다.
- 웹에는 `/`, `/share/$shareId`만 있다. 프로젝트 선택·설정 진입과 공통 API 연결은 조율 담당의 연결 작업이 필요하다.

## 3. 데이터·저장 설계 제안

### IA

`ia_items`에 `id`, `project_id`, `screen_id`, `name`, `description`, `parent_id`, `position`, `revision`, `created_at`, `updated_at`을 둔다.

- `screen_id`는 1~100자, trim한 값만 저장하고 `(project_id, screen_id)` unique로 동시 중복 생성을 막는다. 대소문자를 합치는 타입·인덱스를 사용하지 않는다.
- 이름은 trim 후 1~100자, 설명은 null 또는 최대 2,000자다. 기존 이름 DTO의 trim·공백 검증 보강은 공통 변경 요청이다.
- `(project_id, id)` unique와 `(project_id, parent_id)` 복합 FK로 타 프로젝트 상위를 막는다. 프로젝트·상위 삭제는 restrict, 자기 참조는 check, 다단계 순환은 트랜잭션에서 검증한다.
- `position`은 0 이상의 정수다. 형제 내 동률을 허용하고 `position`, `id` 순으로 정렬한다. 목록은 전체 `{ items }`로 반환하고 화면에서 트리를 만든다. 초기 IA 개수 상한이나 성능 보장은 새로 정하지 않는다.
- 상위 변경·순서 변경도 해당 항목의 revision을 증가시킨다. 초기 UI는 상위 선택과 항목별 순서 값 편집을 제공하는 안이다. 두 형제의 순서를 함께 바꾸는 위/아래 이동·드래그에는 별도 원자적 재정렬 계약이 필요하므로 검토 후 확장한다.

### 기본 양식

`project_templates`는 `project_id`를 PK/FK로 하고 `columns`, `view`의 JSONB 스냅샷, `revision`, `created_at`, `updated_at`을 둔다. 두 배열은 항상 같은 트랜잭션·revision으로 저장한다. JSONB도 외부 DTO 검증을 거치며 DB 타입을 웹에 공유하지 않는다.

- 최초 시스템 열 순서·이름 제안: 케이스 번호, 제목, 사전조건, 수행 단계, 기대 결과, 우선순위, 관련 프레임, IA 화면. 각 열은 별도 UUID를 가진다. 최초 너비는 2B의 시트 기본값과 공통 토큰을 대조해 조율 담당이 하나의 계약으로 정한다.
- 프로젝트 생성 트랜잭션에서 최초 양식 revision 1을 함께 만든다. 기존 프로젝트에는 migration으로 누락 양식만 채우는 안을 추천한다. GET이 데이터를 만들거나 기존 양식을 초기화하지 않는다.
- PUT은 전체 양식을 원자적으로 갱신한다. 기존 시스템 열의 UUID·field는 유지하고, 사용자 열 추가만 새 UUID를 부여한다. 이름 변경을 삭제·재생성으로 처리하지 않는다.
- 새 시트 생성은 저장된 한 revision의 열·표시 설정을 함께 읽어 복사한다. 시트 열에는 새 UUID를 부여하고 view의 참조도 같은 매핑으로 바꾼다. 원본 양식 revision은 추적용 메타데이터로 제안하며 동기화 연결로 사용하지 않는다.
- 양식 변경과 시트 생성이 겹치면 변경 전 또는 후의 완전한 양식 하나만 복사한다. 이미 만들어진 시트의 열·표시·케이스·revision을 변경하지 않는다.

### 참조와 동시성

IA 삭제와 다른 기능의 연결 저장이 경합해도 고아 참조가 없어야 한다.

- 2B는 케이스↔IA 연결을 프로젝트 소속을 포함한 FK 관계로 저장하고 삭제 restrict를 적용해야 한다. JSON 안의 UUID 존재 검사만으로 참조 무결성을 보장했다고 간주하지 않는다.
- IA 트리 변경은 프로젝트 행 잠금 후 부모·조상·revision을 검사한다. 같은 프로젝트의 트리 변경을 직렬화해 서로를 부모로 만드는 동시 요청도 막는다. 잠금 자체가 프로젝트 revision을 올리지는 않는다.
- 2B의 IA 연결 변경과 2C 삭제도 공통 잠금 순서인 프로젝트 → 시트 → IA를 사용하도록 제안한다. 다중 행 잠금은 UUID 순으로 고정한다. 공통 규약은 조율 담당이 반영하고 2B와 교차 검증한다.
- 자식 IA·케이스 참조가 있으면 409 `REFERENCE_IN_USE`로 막는다. 연결을 자동 해제하거나 자식을 연쇄 삭제하지 않는다. 참조 확인과 삭제는 하나의 트랜잭션이다.
- 3A·3B가 나중에 IA 참조를 도입할 때도 FK·삭제 검사에 참여해야 한다. 아직 없는 플로우·후보 테이블을 2C에서 먼저 만들지 않는다.

## 4. API 계약 제안

모든 경로는 `/api/v1/projects/{projectId}` 아래다. operationId·DTO·오류 코드는 조율 담당이 공통 계약에 반영한 후 소비한다.

| 메서드·하위 경로 | 입력·응답 | operationId 제안 |
| --- | --- | --- |
| GET `/ia` | `{ items: IaItem[] }` | `listIaItems` |
| POST `/ia` | 기존 Create DTO → IaItem, 201 | `createIaItem` |
| PATCH `/ia/{itemId}` | expectedRevision + 변경 필드 → IaItem, 200 | `updateIaItem` |
| DELETE `/ia/{itemId}?expectedRevision=` | 양의 정수 기대 revision → 본문 없는 204 | `deleteIaItem` |
| GET `/template` | ProjectTemplate, 200 | `getProjectTemplate` |
| PUT `/template` | 기존 UpdateTemplate DTO → ProjectTemplate, 200 | `updateProjectTemplate` |

`IaItem`은 위 IA 저장 모델의 공개 필드와 UTC ISO 시각을 제공한다. `ProjectTemplate`은 `projectId`, `columns`, `view`, `revision`, `createdAt`, `updatedAt`을 제공한다. DB 내부 정보는 응답하지 않는다.

PATCH는 `expectedRevision`을 필수로 하고 나머지는 부분 수정으로 바꾸는 안을 추천한다. 생략은 유지, description·parentId의 null은 비우기, 변경 필드가 없으면 400이다. nullable 검증을 이유로 screenId·name·position의 null을 허용하지 않는다.

| 조건 | 응답 제안 |
| --- | --- |
| 형식 오류·공백 이름·자기/하위 항목을 부모로 지정·잘못된 양식 | 400 `VALIDATION_ERROR`, 필드·검증 코드 |
| 프로젝트·항목·부모가 없거나 타 프로젝트 소속 | 404 `NOT_FOUND` |
| 같은 프로젝트의 화면 ID 중복 | 409 `SCREEN_ID_CONFLICT`, `screenId` 필드 식별 |
| 수정·삭제의 revision 불일치 | 409 `REVISION_CONFLICT`, `currentRevision` |
| 자식 또는 업무 참조가 남음 | 409 `REFERENCE_IN_USE`, 안전한 참조 종류 |

중복 제약 위반은 예측 가능한 오류로 매핑하고 SQL·제약 이름·원본 예외를 노출하지 않는다. 생성 POST는 자동 재시도하지 않는다. 저장 응답 유실 시 성공을 단정하거나 바로 재전송하지 않고 목록/상세·revision을 다시 확인한다.

## 5. 웹 구성과 편집 상태 제안

진입 경로는 `/projects/$projectId/settings`를 제안한다. 페이지는 `projectId`를 props로 받고 앱 라우트·provider 내부에 의존하지 않는다. 라우트와 프로젝트 선택·다른 업무 화면의 설정 진입 링크는 조율 담당이 연결한다.

- 프로젝트 정보, IA, 기본 양식을 구분한다. 프로젝트 이름·설명 편집 포함 여부는 검토 항목이다. 프로젝트 생성 화면을 이 페이지에 새로 만들지는 않는다.
- IA는 계층이 보이는 목록과 선택 항목 편집 영역을 둔다. 화면 ID·이름·상위 항목·설명·순서 값을 편집하고 저장한다. 부모 선택에서 자신·후손을 제외하되 서버도 검증한다.
- 기본 양식은 현재 표시 순서의 열 목록에서 이름·너비를 편집하고 위/아래 버튼으로 순서를 바꾼다. 사용자 열은 추가·삭제하고 시스템 열의 삭제 행동은 제공하지 않는다. 케이스 값 입력 표는 2B에 둔다.
- 설정에는 명시적인 저장·취소를 제안한다. IA는 항목별, 기본 양식은 전체 단위로 저장하고 요청 중 해당 편집 단위만 중복 제출을 막는다. 2B 시트 자동 저장과 별개의 설정 편집 계약이다.
- 서버 조회는 TanStack Query, 초안·선택·저장 중 상태는 페이지 내부 상태로 관리한다. 이 범위에는 새 Zustand 저장소나 UI 의존성이 필요하지 않다.
- 조회 갱신·409·네트워크 오류에서 입력을 유지한다. 충돌 시 최신 저장 내용을 별도로 확인하고 사용자가 초안을 버리거나 최신 버전 기준으로 다시 편집한다. revision만 바꿔 같은 초안을 강제 저장하는 기능은 제공하지 않는다.
- 미저장 상태에서 항목·탭·프로젝트 이동 시 저장/버리기/계속 편집을 선택하게 하는 안이다. 브라우저 종료·새로고침은 기본 이탈 확인 범위이며 재시작 후 초안 복원을 약속하지 않는다. 앱 이동 차단 연결은 조율 담당과 맞춘다.
- 삭제는 대상을 확인한 후 수행한다. 참조 중이면 연결 해제 필요성을 안내하고 초안을 유지한다. 양식 변경은 새 시트에만 적용된다는 정보는 양식 저장 판단 위치에 표시한다.

기존 `@cheddar/ui`와 토큰을 사용한다. 별도 트리 라이브러리·아이콘·드래그 도구·공통 토큰 추가 요청은 현재 없다. 레이블·오류 연결, 키보드 조작, Dialog 포커스를 확인하고 구현 후 독립 UX 문구 검수를 수행한다. 이 문서의 화면 설명은 최종 UI 문구가 아니다.

## 6. 새 경로와 파일 소유권

다음 세 소스 폴더는 초안 당시 허용 구조 밖이었으며 2026-10-15 사용자가 생성 승인했다. 공통 `ff4e09c`에 허용 구조 반영 후 하위 세그먼트 폴더 없이 구현했다.

| 정확한 저장소 상대 경로 | 목적·예상 영속 파일 | 영향 |

| `apps/api/src/ia/` | `ia.module.ts`, `ia.controller.ts`, `ia.service.ts`, `ia.repository.ts` | IA API·트리·참조 검사. 공통 schema·계약 소비 |

## 7. 공통 변경 요청과 통합 순서

아래 파일은 2C가 직접 수정하지 않는다. 조율 채팅 `01a13d09-b1e9-7b31-ac07-0e6f6b3ab6f6`이 공통 커밋으로 전달한다. 2026-10-15 사용자가 이 채팅에서 공통 요청 전달을 직접 지시했고, 조율 채팅과의 완료 보고·개발 조율 메시지를 허용했다. 다른 기능 채팅끼리의 직접 메시지는 포함하지 않는다.

| 우선순위 | 담당 경로·계약 | 요청 |
| --- | --- | --- |
| 선행 | `apps/api/src/contracts/ia.dto.ts`, 필요 시 `sheets.dto.ts`, 공통 계약 테스트 | 응답 DTO·목록·삭제 query, PATCH 의미, 안전한 오류 코드 확정. 초기 열 이름·너비·복사 UUID 정책을 2B와 통일 |
| 선행 | `apps/api/src/database/schema.ts`, `migrations/`, `projects/` | IA·양식 테이블/제약, 기존 프로젝트 양식 보충, 프로젝트 생성 시 양식 초기화. 2B 케이스↔IA FK와 잠금 순서 합의 |
| API 연결 | `apps/api/src/app.module.ts` | 두 기능 module 등록. 2B가 같은 트랜잭션에서 저장 양식을 읽는 module/repository 공개 경계 연결 |
| API 연결 | `apps/api/openapi.json`, 두 앱 생성 SDK, 공통 API 테스트 | 선행 DTO 반영 후 기능 controller 완성 → 실제 경로 명세 export → SDK 재생성·명세 일치 검사. 가짜 실행 경로 선등록 금지 |
| 웹 연결 | 웹 `src/app/`, `src/shared/api/`, `src/shared/config/` | 설정 라우트·진입 링크·API client·이탈 차단 연결. 페이지 내부에서 공통 client 재구성 금지 |
| 검증 전 | API 테스트 보조·설정, 환경·CORS | 전용 테스트 파일에서도 기존 DB/role 검사·advisory lock·자기 데이터만 정리하는 보조 경계. 공유 DB 테스트 순차 실행. 포트 3104/5177은 점유·CORS 확인 후 결정 |
| 승인 반영 | `docs/architecture.md`, 필요 시 `product.md` | 승인된 새 폴더·설정 저장 방식·확정 계약 반영. 정책을 2C가 먼저 수정하지 않음 |

추가 의존성·공통 UI·토큰 변경은 현재 요청하지 않는다. 필요성이 새로 확인되면 정확한 대상·이유를 추가한다.

통합 순서는 공통 데이터/DTO → 2C API → module·명세·SDK → 2C 화면·라우트 → 2B 복사/참조 교차 검증이다. 공통 계약 전에는 임시 DTO·SDK·가짜 API를 복제해 구현하지 않는다.

## 8. 구현 순서와 검증 계획

| 순서 | 작업 | 확인할 결과 |
| --- | --- | --- |
| 1 | 사용자 검토 결과·승인 경로·조율 공통 커밋 확인 | 미정 계약·파일 담당·실행 DB/포트가 명확함 |
| 2 | IA repository/service/controller·업무 테스트 | 중복·프로젝트 경계·순환·revision·삭제 제한·동시 요청 검증 |
| 3 | 양식 repository/service/controller·업무 테스트 | 양식 초기 상태·원자적 전체 저장·충돌·잘못된 열·불변 식별자 검증 |
| 4 | 조율 담당의 module·OpenAPI·SDK 연결 | 실제 HTTP와 명세 일치, 생성 SDK가 두 앱에서 타입 검사 통과 |
| 5 | 설정 화면·초안·저장·오류 처리와 앱 연결 | 실제 API로 등록·편집·재조회, 실패·충돌 시 입력 보존 |
| 6 | 2B 교차 검증·독립 문구 검수·최종 확인 | 양식 복사·기존 시트 불변·참조 경합, 문구 지적 반영, 변경 diff·산출물 확인 |

API는 기존 node:test·실제 PostgreSQL/HTTP 체계를 사용한다. 중요한 검증 사례:

- 같은 프로젝트 중복은 동시 생성/수정에서도 한 요청만 성공, 다른 프로젝트 동일 ID 및 `ORD-01`/`ord-01`은 허용, trim 후 중복 차단.
- 없는 프로젝트·타 프로젝트 부모/항목·자기 부모·다단계 순환·동시 상호 부모 변경 차단, 오류 후 데이터 보존.
- 같은 revision 수정/삭제 경쟁, 자식·케이스 참조 삭제 차단, 화면 ID 변경 후 기존 연결 UUID 유지, 연결 저장과 삭제 경합에서 고아 참조 없음.
- 시스템 열 누락/중복/field 교체·UUID 교체·잘못된 사용자 유형·view 불일치 거부. 양식 저장과 표시 설정이 함께 반영되거나 함께 실패.
- 기존 프로젝트 backfill이 저장 양식을 덮어쓰지 않음. 프로젝트 생성과 양식 초기화가 함께 성공/실패하며 GET 반복 조회는 변경을 만들지 않음.
- 양식 A에서 생성한 시트 S1은 B로 바꾼 후에도 열·값·revision 불변. 새 S2는 B의 독립 UUID·표시 사본을 사용하고 복사/갱신 경합에도 혼합 양식이 생기지 않음. 이 검증은 2B 기능 통합 후에 수행.

브라우저에서는 한글 조합 입력, 필수 입력·오류 포커스, 상위 선택, 키보드 열 순서 조절·너비 저장, 미저장 이동 확인, 느린 요청·오프라인·409 후 초안 유지, 새로고침 후 저장값을 확인한다. UI 테스트 도구 도입은 미정이므로 새 패키지를 전제하지 않고 실제 화면 검증 근거를 남긴다. 문구 구현 후 workflow의 지정 독립 에이전트 검수를 받는다.

승인 후 실행할 기본 검사: `pnpm check`, `pnpm --filter @cheddar/api test`, `pnpm --filter @cheddar/api openapi:check`. DB 테스트는 조율한 환경에서 순차 실행하며 SDK 재생성은 조율 담당이 수행한다. 테스트 출력·로그·스크린샷은 OS 임시 경로에 둔다. 이번 설계 작성에서는 설치·빌드·서비스·DB·AI를 실행하지 않는다.

## 9. 승인된 추천안과 공통 계약 확정

| 항목 | 추천안 | 대안·영향 |
