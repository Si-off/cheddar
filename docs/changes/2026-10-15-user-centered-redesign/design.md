# Cheddar 사용자 중심 UX 설계안

작성일: 2026-10-15. 상태: 사용자 검토용 제안. 실제 제품 구현·사용성 검증 완료를 뜻하지 않는다.

## 1. 출발점과 설계의 경계

사람이 직접 수행할 QA 케이스를 만들고 전달하는 작업을 중심에 둔다. 사용자는 디자인 도구에서는 필요한 화면을 고르고, 웹에서는 테스트할 범위를 정한 뒤 결과를 자신의 업무 문서로 완성한다.

참조한 원천은 현재 `docs/product.md`, `docs/architecture.md`, `docs/workflow.md`, `docs/ux-writing.md`, `DESIGN.md`, `packages/design-tokens/src/theme.css`다. 현재 UI 소스, 기존 스크린샷, 과거 작업 설계안, 이전 생성 레퍼런스는 열지 않았다. 이미지 편집에 사용한 입력은 이번 대화에서 새로 만든 이미지뿐이다.

### 유지하는 제품 계약

- 플러그인은 선택한 Frame 또는 Section 내부 최상위 Frame의 데이터와 이미지를 프로젝트에 업로드한다.
- 프로젝트 아래에 업로드 묶음, 시트, 화면 목록(IA), 기본 양식이 있다.
- 빈 시트부터 작성하거나 자료·설명을 바탕으로 AI 생성할 수 있다. 생성은 새 시트 또는 기존 시트 교체다.
- 편집은 표 중심이며 사용자 열과 긴 문자열을 지원한다. 추론·모호함이 있는 결과는 별도 후보로 다룬다.
- 생성 중에는 대상 시트만 잠그고 실패하면 이전 내용을 보존한다. 자동 재시도는 하지 않는다.
- XLSX는 저장된 현재 시트 전체 케이스를 현재 열 이름·순서로 내보낸다. 검색 결과만 내보내거나 후보를 포함하지 않는다.
- 초기 로컬 환경에는 로그인·계정·팀 관리가 없다. 공유는 후속 읽기 전용 기능이다.

### 이번에 새로 제안하는 UX

- 프로젝트의 기본 진입점을 테스트 시트 목록으로 둔다.
- 자료 업로드가 끝나면 해당 프로젝트·업로드가 선택된 생성 준비 화면으로 연결한다.
- 생성 준비는 한 화면에서 범위·자료·설명을 확인한다. 강제 순차 마법사를 두지 않는다.
- 케이스 편집과 후보 검토를 시트 안의 별도 탭으로 구분한다.
- 상세 패널은 필요할 때 열고, 자료와 케이스의 관계를 확인하는 데 사용한다.
- 공유 정책은 별도 제안으로 남긴다. 사용자 조사로 검증된 결정으로 표현하지 않는다.

## 2. 사용자와 작업 맥락

아래는 권한 체계나 확정 페르소나가 아니라 설계 가설이다. 한 사람이 여러 역할을 맡을 수 있다.

| 작업 역할 | 시작 상황 | 끝내려는 일 | 설계 대응 |
| --- | --- | --- | --- |
| 자료를 준비하는 사람 | Figma에서 수정한 화면을 보고 있음 | 필요한 화면을 정확한 프로젝트에 전달 | 프로젝트와 선택 프레임만 확인하고 업로드 |
| 케이스 작성자 | 기능·변경 범위를 알고 있음 | 실행 가능한 단계와 기대 결과 작성 | 범위·설명 입력, 표 편집, 자료 확인 |
| 케이스 검토자 | AI 초안이나 동료 문서를 받음 | 근거가 불확실한 항목을 판단 | 후보 이유와 관련 자료를 함께 확인 |
| 전달받는 사람 | QA 수행을 위해 문서가 필요함 | 케이스를 찾고 내용을 이해 | XLSX, 후속 읽기 전용 열람 |

설계상 우선순위는 처음 업로드한 사람의 생성 진입, 매일 돌아오는 작성자의 편집 재개, 후보 판단, 전달 순서다. 테스트 실행 결과 기록·결함 관리·담당자 배정은 현재 제품 범위에 추가하지 않는다.

## 3. 정보 구조와 용어

```text
프로젝트 선택 / 새 프로젝트
└─ 프로젝트
   ├─ 테스트 시트                         기본 진입점
   │  ├─ 새 테스트 시트                  범위·자료·설명 → 생성 또는 빈 시트
   │  └─ 시트
   │     ├─ 케이스                       표 + 선택적 상세 패널
   │     ├─ 검토할 후보                  이유 확인 → 수정·추가·제외
   │     ├─ 다시 생성                    추가 메뉴에서 진입
   │     └─ XLSX 내보내기
   ├─ 디자인 자료                        업로드 묶음 → 프레임
   ├─ 화면 목록                          IA 계층·화면 ID·이름
   ├─ 기본 양식                          이후 생성할 시트의 열 구성
   └─ 프로젝트 설정                      이름·설명

후속: 시트 공유 → 별도의 읽기 전용 열람 화면
```

- 사이드바는 프로젝트 탐색만 맡는다. 시트의 검색·열 설정·내보내기는 시트 화면에 둔다.
- `화면 목록`은 IA의 사용자 노출 이름이다. Figma 프레임과 같은 대상인 것처럼 합치지 않는다.
- `화면·기능` / `사용자 흐름`은 제품 계약의 단위 / 통합 QA 범위를 표현하는 제안이다. 개발 코드 테스트로 오해할 수 있는 용어를 피한다.
- 후보는 케이스에 포함되지 않은 항목이다. `검토할 후보` 탭 숫자는 대기 중인 항목 수다. 완료한 후보는 필터로 다시 볼 수 있다.
- 시트에 연결된 프레임은 현재 Figma 화면과 자동 동기화된다고 표현하지 않는다. 업로드 시점의 자료다.

## 4. 주요 사용자 흐름

### A. Figma에서 첫 케이스까지

1. Figma에서 Frame 또는 Section 선택.
2. 플러그인에서 프로젝트와 썸네일·프레임 이름 확인.
3. `프레임 3개 업로드` 실행. 클릭 시점의 프로젝트·목록을 고정한다.
4. 업로드 완료가 확인되면 `웹에서 테스트 케이스 만들기` 선택.
5. 웹은 해당 프로젝트와 방금 올린 자료가 선택된 새 시트 화면을 연다. 이 이동만으로 AI를 실행하지 않는다.
6. 사용자가 시트 이름, 테스트 범위, 확인할 내용, AI 모델을 확인하고 `케이스 생성` 실행.
7. 대상 시트에서 생성 상태를 확인. 성공하면 케이스 탭으로 이동하고 후보가 있으면 탭에 개수를 표시.
8. 케이스를 수정하고 후보를 판단한 뒤 XLSX로 전달.

자료 식별자를 URL로 전달하는 구체적 방법과 로컬 Figma→브라우저 전환은 구현 시 검증 대상이다. 링크로 열어도 프로젝트·자료 소속을 다시 확인하며 URL 값만 믿고 다른 프로젝트의 자료를 연결하지 않는다.

### B. 웹에서 시작

프로젝트 선택 → `새 시트` → 기존 디자인 자료 선택 또는 설명 입력 → 생성. 자료 없이 설명만으로도 진행할 수 있다. Figma 업로드를 필수 온보딩으로 만들지 않는다.

### C. 직접 작성

`새 시트` → 이름 확인 → `빈 시트로 시작` → 첫 행 편집. AI용 필수 입력 검증을 이 경로에 적용하지 않는다. 기본 양식을 복사하되 빈 초안 저장을 허용한다.

### D. 반복 편집

프로젝트의 시트 목록 → 제목으로 시트 열기 → 검색·표 편집 → 필요한 케이스만 상세 패널 열기. 최근 수정 시트를 상단에 정렬하는 것을 추천한다. 진행률·완료율은 사람의 QA 수행 상태가 없으므로 만들지 않는다.

### E. 새 디자인으로 다시 생성

새 업로드 → 기존 시트의 추가 메뉴에서 `다시 생성` → 자료·설명 확인 → 기존 내용 교체 확인 → 생성. 기존 입력이 저장되기 전에는 교체를 시작하지 않는다. 자료를 업로드했다고 기존 시트가 자동 갱신되지 않는다.

### F. 후보 판단

`검토할 후보` → 한 항목 선택 → 후보로 남은 이유와 수행 단계·기대 결과·관련 프레임 확인 → 필요시 수정 → `케이스에 추가` 또는 `제외`. 연결된 IA가 없다는 이유만으로 후보가 되지는 않는다.

### G. 전달

현재 시트의 저장 완료 확인 → `XLSX 내보내기` → 전체 케이스의 파일을 받는다. 후속 공유 도입 시에는 시트에서 링크를 만들고 수신자는 프로젝트 관리 화면을 거치지 않고 케이스를 열람한다.

## 5. 플러그인 화면과 상태

### P1. 업로드 준비

위에서부터 Cheddar 이름, 프로젝트 선택, 선택 프레임 목록, 업로드 버튼 순이다. 목록 행에는 썸네일과 이름만 둔다. 선택 항목이 많으면 목록만 스크롤하고 프로젝트·하단 행동은 접근 가능하게 유지한다.

프로젝트의 이름이 같아 구분이 필요한 경우 선택 메뉴 안에서 설명을 추가로 보여준다. 프레임도 이름이 같은 항목에 한해 상위 Section이나 페이지 이름을 보여주는 방안을 사용한다. 전체 행에 상시 메타데이터를 깔지 않는다.

- 정상 연결 배지, 프레임 크기, node ID, 순번, 선택 동작 설명을 넣지 않는다.
- 빈 선택에서만 `Figma에서 프레임이나 섹션을 선택하세요.`를 표시한다. 목록이 채워지면 제거한다.
- 프로젝트가 없을 때는 `프로젝트 만들기`로 웹의 프로젝트 생성에 연결한다. 플러그인에 별도 설정 화면을 중복 구현하지 않는 제안이다.
- 초기 최근 프로젝트 자동 선택 여부는 결정 사항이다. 추천은 직전 선택 복원과 프로젝트 이름의 명확한 표시다. 자동 업로드는 하지 않는다.
- 지원하지 않는 선택이 섞였으면 해당 대상을 알리고 수정하게 한다. 이를 조용히 제외하고 성공으로 표시하지 않는다.

### P2. 업로드 중

대상 프로젝트·목록은 읽기 전용이다. 관측 가능한 진행만 표시한다. 프레임 처리 수가 실제 전달되는 경우 `2 / 3`을 사용하고, 그렇지 않으면 `업로드 중`만 표시한다. 임의 퍼센트나 남은 시간을 만들지 않는다.

프레임별 완료 표시가 있더라도 전체 묶음 등록 완료 전에는 성공 화면으로 전환하지 않는다. 전체 전송을 마친 뒤 묶음 등록 중에는 `업로드 마무리 중`으로 구분한다. 창을 열어 두라는 안내는 현재 시안에서 제외한다. 실제 구현에서 창 종료가 업로드를 중단시키는지 확인한 뒤에만 필요성을 판단한다.

### P3. 완료

`프레임 3개 업로드 완료`, 업로드한 프로젝트, 프레임 목록, `웹에서 테스트 케이스 만들기`, `계속 업로드`를 제공한다. 프로젝트는 변경할 수 없는 결과 정보다. `계속 업로드`를 누르면 현재 Figma 선택을 다시 읽어 준비 상태로 돌아간다. 재업로드는 새 묶음이며 기존 업로드 교체가 아니다.

### P4. 연결·선택·업로드 오류

| 조건 | 보여줄 내용 | 사용자 행동 / 보존 |
| --- | --- | --- |
| 서버에 연결되지 않음 | `프로젝트를 불러오지 못했습니다.` | `다시 연결`, 선택 프레임은 유지. 연결 설정은 필요 시 펼침 |
| 미지원 선택 혼합 | 지원하지 않는 대상 이름과 `프레임이나 섹션을 선택하세요.` | Figma에서 선택 수정, 업로드 실행 불가 |
| 빈 Section | 해당 Section 이름과 `선택한 섹션에 프레임이 없습니다.` | 선택 수정 |
| 추출 중 삭제·변경 | `선택한 프레임이 변경됐습니다. 목록을 다시 확인하세요.` | 목록 새로 확인 후 사용자 재실행 |
| 일부 파일 전송 실패 | `업로드를 완료하지 못했습니다.`와 실패 대상 | 성공한 묶음처럼 표시하지 않음. 수동 재시도의 중복 방지 여부는 계약 확인 후 연결 |
| 완료 후 웹 열기 실패 | 업로드 완료 상태를 유지 | 웹 열기 재시도. 업로드를 다시 시키지 않음 |

## 6. 웹 주요 화면

### W1. 프로젝트 선택과 시트 목록

프로젝트가 없으면 프로젝트 이름 입력과 생성 행동을 제공한다. 이름 1~100자 규칙을 적용하고, 중복 이름은 허용한다. 프로젝트가 있으면 이름과 설명으로 선택한다.

프로젝트 진입 후에는 시트 목록이 중심이다. 행에는 시트 이름, 케이스 수, 수정 시각을 둔다. 생성 중·실패 등 작업에 영향을 주는 상태만 추가한다. 첫 시트가 없으면 `테스트 시트가 없습니다.`와 `새 시트`를 제시한다. 거대한 환영 영역·통계 카드·튜토리얼을 추가하지 않는다.

### W2. 디자인 자료

업로드 묶음 목록과 선택한 묶음의 프레임 목록을 제공한다. 여러 묶음을 구분하는 데 필요한 업로드 날짜·시간은 목록에서 사용한다. 프레임은 썸네일과 이름으로 선택한다.

선택 후 `선택한 자료로 시트 만들기`로 생성 준비에 진입한다. 미리보기 확대는 프레임 내용 확인용이다. 초기 제외된 삭제·버전 교체·자동 동기화는 제시하지 않는다. 자료가 없으면 Figma 플러그인으로 가져올 수 있는 진입 경로를 제공하되 직접 시트 작성을 막지 않는다.

### W3. 새 테스트 시트 / 생성 준비

화면의 핵심 질문은 무엇을 테스트하고 무엇을 근거로 만들 것인가다. 제목은 `새 테스트 시트`로 간결하게 둔다.

| 순서 | 요소 | 동작 |
| --- | --- | --- |
| 1 | 시트 이름 | 결과 문서의 이름 입력 |
| 2 | 테스트 범위 | `화면·기능` 또는 `사용자 흐름`. 플러그인 진입만으로 범위를 단정하지 않음 |
| 3 | 확인할 내용 | 사용자의 목적·주요 예외 입력. 상시 예시 문단을 본문에 두지 않음 |
| 4 | 디자인 자료 | 업로드 묶음별 프레임 선택. 미리보기는 오른쪽, 좁으면 펼침 영역 |
| 5 | 화면 연결·양식 | 선택 요약을 가진 접힘 영역. 필요한 경우만 편집 |
| 6 | AI 모델 | Claude Haiku / OpenAI Luna 선택과 해당 제공자 전송 안내 |
| 7 | 행동 | `빈 시트로 시작`, `케이스 생성` |

자료·설명이 모두 없으면 생성 행동 옆에 `디자인 자료를 선택하거나 확인할 내용을 입력하세요.`를 표시한다. 이미지 없이 설명만 있는 경우에는 프레임 미리보기 패널을 표시하지 않는다. 시트 이름·범위·프레임 수를 다시 정리하는 요약 카드는 두지 않는다.

모델 옆에는 해당 실행에 실제 포함되는 자료의 외부 전송 사실을 표시한다. 예: `선택한 디자인 자료, 화면 목록, 시트 양식과 입력 내용이 Claude에 전송됩니다.` 실행에 포함되지 않는 항목은 나열하지 않고 제공자 이름은 선택 모델에 맞춘다. 기존 시트의 예시가 포함되는 재생성에서는 기존 케이스도 전송됨을 안내한다. 중요 조건을 툴팁에 숨기지 않는다.

흐름도는 후속 연결 기능이다. 통합 생성의 필수 입력으로 만들지 않고 초기 시안에는 미구현 편집기를 노출하지 않는다. 도입 시 `흐름` 펼침 영역에서 순서·분기와 IA 연결을 검토할 수 있도록 한다.

### W4. 생성 중·성공·실패

- 실행 버튼은 중복 제출을 막는다. 대상 시트 안에서 `케이스 생성 중` 상태를 보여주며 다른 시트 탐색은 허용한다.
- 기존 시트는 이전 케이스를 읽을 수 있되 편집·후보 추가·재생성은 잠근다. 읽는 내용이 새 결과라고 오해되지 않도록 상태를 같은 위치에 둔다.
- 확인되지 않은 단계·가짜 진행률·예상 소요 시간을 표시하지 않는다. 실제 작업 상태로 알 수 있는 정보만 쓴다.
- 성공한 결과가 저장된 뒤 표를 바꾼다. 확인된 케이스 수와 검토 대기 후보 수만 표시한다. AI 신뢰도 점수나 사람이 검토 완료했다는 배지를 만들지 않는다.
- 실패 시 `케이스를 생성하지 못했습니다.`와 대응 가능한 원인을 보여준다. 이전 내용 보존이 실제 확인된 경우에만 `기존 케이스는 유지됩니다.`를 덧붙인다.
- 자동 재시도 없이 `생성 설정 확인`으로 입력을 고친 뒤 다시 실행한다. 출력 한도 초과나 입력 크기 초과를 네트워크 오류처럼 뭉개지 않는다.
- 화면에 돌아오면 생성 상태를 조회한다. 서버 중단 작업의 실패 판정 시간은 현재 제품 계약을 따르며, 재방문만으로 새 AI 호출을 하지 않는다.

### W5. 케이스 편집

상단에 시트 이름과 저장 상태, XLSX 내보내기, 추가 메뉴를 둔다. 그 아래 `케이스` / `검토할 후보` 탭, 검색·열 설정·케이스 추가 도구, 표 순서다. `다시 생성`은 일상 편집 중 실수로 누르지 않도록 추가 메뉴에 둔다.

표는 번호·제목·사전조건·수행 단계·기대 결과·우선순위·프레임 연결·화면 연결과 사용자 열을 담는다. 현재 열 순서를 존중하며 긴 문자열을 줄바꿈하고 행 높이를 늘린다. 제목과 번호가 맥락을 유지하도록 고정할 것을 추천하되 작은 화면에서 고정 영역이 내용을 압박하면 번호만 고정한다.

셀 선택과 편집을 구분한다. 첫 클릭은 선택, Enter 또는 더블클릭으로 편집, 편집 중 Escape는 현재 편집 진입 이후 값을 되돌린다. 저장 완료된 변경까지 복원하는 기능으로 표현하지 않는다. IME 조합 중 Enter로 편집을 끝내지 않는다. 다중행 입력에서 Enter는 줄바꿈, Ctrl/Cmd+Enter는 편집 완료다. 표 탐색 상태에서는 방향키로 이동하고 Tab으로 다음 셀에 이동한다. 자세한 키 안내는 별도 필요가 검증된 경우에만 제공한다.

번호 옆 상세 열기 행동 또는 키보드로 케이스를 열면 오른쪽 패널이 나타난다. 케이스 필드, 연결된 프레임, 화면 목록 연결을 편집한다. 패널과 표는 같은 초안을 사용하고 이중 저장 버튼을 만들지 않는다. 패널 닫기 후 원래 케이스로 포커스를 돌려준다.

복붙은 행·열 위치를 유지하고 사용자 입력을 임의 변환하지 않는다. 범위를 벗어나거나 붙일 수 없는 값은 버리지 말고 적용하지 않은 위치와 해결 행동을 알린다. 정확한 붙여넣기 계약은 구현 전 현재 데이터 계약과 대조한다.

### W6. 검토할 후보

후보 목록에는 제목과 후보로 남은 이유를 보여준다. 선택한 후보의 내용과 관련 프레임을 같은 작업 영역에서 확인한다. 원시 모델 출력·확률·내부 검사 코드는 노출하지 않는다.

`케이스에 추가`는 사용자가 이 내용을 QA 케이스로 사용할 의사가 있음을 뜻한다. 수정 후 추가할 수 있다. 성공 응답 전에는 목록에서 사라지거나 추가됨으로 표시하지 않는다. 저장 실패 시 입력과 선택을 보존한다. `제외`는 후보 상태 변경이고 데이터 영구 삭제가 아니다. `제외됨` 보기에서 `검토로 되돌리기`를 제공한다. 추가된 후보에는 연결된 케이스를 열 수 있는 행동을 둔다.

대기 후보가 없으면 `검토할 후보가 없습니다.`를 표시한다. 케이스 0개·후보만 존재하는 생성 결과에서도 오류처럼 처리하거나 빈 케이스 표만 보여주지 않고 후보 탭으로 안내한다.

### W7. 화면 목록·기본 양식·프로젝트 설정

- 화면 목록: 화면 ID·이름·계층을 관리한다. 케이스에 참조된 항목 삭제는 연결을 먼저 해제하도록 안내한다. 화면 ID 변경으로 연결을 잃지 않는다.
- 파일 분석 후속 기능: XLSX·CSV를 분석한 결과를 검토·수정한 뒤 확정한다. 파일 선택 즉시 기존 화면 목록을 교체하지 않는다.
- 기본 양식: 열 이름·순서·너비와 사용자 열을 편집한다. 이 화면에는 `새 시트에 적용됩니다.`를 유지한다. 기존 시트도 바뀐다고 오해하면 사용자의 선택에 영향을 주기 때문이다.
- 열 설정: 시스템 열은 이름·순서·너비를 수정하고 삭제하지 않는다. 사용자 열 삭제 확인에서는 해당 열 값이 함께 삭제됨을 알린다.
- 프로젝트 설정: 이름과 설명을 편집한다. 로그인·멤버·과금·삭제 기능을 임의로 추가하지 않는다.

## 7. 저장과 전달의 예외 처리

| 상황 | 화면 반응 | 보존·후속 행동 |
| --- | --- | --- |
| 수정 직후 | `저장 중` | 계속 입력할 수 있음 |
| 서버 저장 성공 | `저장됨` | 성공 응답으로만 전환 |
| 서버 저장 실패 | `저장하지 못했습니다.` | 입력 유지, 수동 재시도 |
| 미저장 상태에서 시트 이동 | 로컬 보관 성공 여부 확인 후 이동 선택 | 성공 확인 없이 `보관됨` 표시 금지 |
| 서버·로컬 보관 모두 실패 | 이동을 막고 입력 유지 | 복사 등 실제 가능한 보존 행동 제시 |
| 다른 변경과 충돌 | `다른 변경이 있어 저장하지 못했습니다.` | 자신의 입력 보존, 최신 내용 확인. 강제 덮어쓰기 제안 금지 |
| 검색 결과 없음 | `검색 결과가 없습니다.` | `검색 지우기`, 새 시트 생성으로 유도하지 않음 |
| 검색 중 XLSX 선택 | 전체 케이스 내보내기 범위 안내 | `검색과 관계없이 전체 케이스를 내보냅니다. 후보는 포함하지 않습니다.` |
| 미저장 상태에서 XLSX 선택 | 먼저 저장 완료를 기다림 | 저장 실패하면 다운로드하지 않고 저장 문제 해결 |
| XLSX 요청 실패 | `파일을 만들지 못했습니다.` | 현재 편집 상태를 유지하고 수동 재시도 |

XLSX 안내는 내보내기 진입 시에만 보여준다. 후보가 있거나 검색이 활성화된 경우 특히 범위를 명확히 한다. 항상 화면 아래에 설명을 반복하지 않는다.

## 8. 후속 읽기 전용 공유 설계

현재 로컬 MVP에 동작하는 공유 버튼을 그려 넣지 않는다. 아래는 접근 정책·서버 제공 범위 결정 후 구현할 제안이다.

### 발신자

시트의 `공유` → 공유 범위·접근 조건 확인 → 링크 만들기 → 링크 복사. 읽기 전용임을 명시하고 케이스 외에 무엇이 포함되는지 결정하기 전에 링크를 발급하지 않는다.

추천 초기 범위는 저장된 케이스와 현재 열 구성이다. 후보·다른 시트·프로젝트 설정은 포함하지 않는다. 원본 프레임 이미지도 기본 제외를 추천한다. 이미지가 필요하면 별도 포함 여부와 접근 경계를 정한다. 이는 아직 확정되지 않은 제품 정책이다.

### 수신자

시트 제목, `읽기 전용`, 케이스 검색과 표, 긴 내용을 읽는 상세 패널을 제공한다. 프로젝트 관리 사이드바와 편집·생성·후보 행동은 없다. 권한이 없거나 링크를 사용할 수 없으면 내용 없이 `이 링크를 사용할 수 없습니다.`로 표시한다. XLSX 다운로드 허용 여부는 별도 정책으로 결정한다.

### 필요한 결정과 추천

| 결정 | 대안과 영향 | 추천 |
| --- | --- | --- |
| 접근 범위 | 익명 링크는 접근이 쉽지만 링크 전달로 열람자가 늘어남. 사내 접근은 배포·접근 제어가 필요 | 초기 로컬 MVP는 XLSX 유지. 공유 구현 때 실제 배포 범위와 함께 결정 |
| 변경 반영 | 실시간 시트는 항상 최신이나 수신 중 내용이 바뀜. 고정본은 전달 기준이 명확하나 재공유 필요 | QA 전달 목적에는 고정본 우선 검토. 저장·버전 계약 확장 필요 |
| 만료·회수 | 무기한 링크는 편하지만 공개 지속. 만료·회수는 운영 계약 필요 | 최소 수동 회수 포함을 추천하되 승인 전 구현하지 않음 |
| 자료·다운로드 | 케이스만 공유하면 노출 범위가 작음. 프레임·XLSX 포함은 수신 활용성 증가 | 케이스만 기본, 자료·다운로드는 별도 결정 |

## 9. 시각·상호작용 기준

- `DESIGN.md`와 공통 토큰을 그대로 기준으로 사용한다. primary는 주요 행동과 현재 선택에 집중한다. 정보량을 늘리기 위한 배지·카드·아이콘을 추가하지 않는다.
- 표는 비교를 위해 경계를 쓰고, 일반 화면의 그룹은 여백으로 우선 구분한다. 시트 작업 영역은 넓게 사용하고 생성 폼은 읽기 쉬운 폭을 유지한다.
- 본문·레이블·제목은 공통 typography 토큰, 표·컨트롤 간격은 공통 spacing, 모서리는 control/panel/dialog 토큰을 사용한다. 이미지의 임의 색·크기를 새로운 토큰으로 채택하지 않는다.
- 선택은 배경과 경계색, 입력 포커스는 기존 테두리 색으로 표시한다. 요소 크기·위치를 움직여 강조하지 않는다. 선택과 키보드 포커스가 겹쳐도 식별 가능해야 한다.
- 상태 전환은 feedback 120ms, state 180ms, selection 240ms 등 기존 토큰 역할에 맞춘다. 결과 대기 중 시각 효과로 가짜 진행을 만들지 않는다.
- 일반 버튼은 명확한 텍스트를 쓰고 아이콘 전용 버튼에는 접근성 이름을 준다. 툴팁은 기본 추가하지 않는다.

### 화면 크기와 입력 방식

| 조건 | 제안 |
| --- | --- |
| 넓은 웹 작업 공간 | 프로젝트 탐색 + 표 + 선택적 상세 패널 |
| 표와 패널이 함께 읽히지 않는 폭 | 패널을 겹침 패널로 전환, 닫으면 선택 셀로 복귀 |
| 좁은 웹 화면 | 탐색은 접고 표 영역만 가로 스크롤. 전체 페이지의 가로 스크롤 방지 |
| 생성 폼의 두 열이 맞지 않는 폭 | 미리보기는 자료 영역에서 펼침. 폼 순서는 동일 |
| 작은 플러그인 창 | 내용 목록 스크롤, 주요 행동은 가려지지 않게 배치 |
| 키보드·확대 | 논리적 읽기 순서, 포커스 복귀, 텍스트 확대 시 버튼 줄바꿈 허용 |

고정 기기 이름만으로 분기하지 않고 실제 콘텐츠가 읽히지 않는 지점에서 레이아웃을 바꾼다. 구현 검증 시작 크기 제안은 웹 1440×900 / 1024×768 / 390×844, 플러그인 360×600 / 440×720과 200% 확대다. 지원 범위 확정이나 검증 완료 수치가 아니다.

## 10. 문구의 표시 조건

사용자의 후속 지시에 따라 선택 변경 설명과 프레임 크기는 제거한다. 사실 여부와 별개로 지금 판단에 필요하지 않은 정보는 기본 표시하지 않는다.

| 문구·정보 | 표시 여부 | 근거 |
| --- | --- | --- |
| 선택을 바꾸면 목록이 바뀐다는 안내 | 제거 | 실제 목록 변화가 전달함 |
| Frame 1, 크기, node ID | 제거 | 썸네일·이름 외에 업로드 결정에 필요 없음 |
| 정상 `연결됨` | 제거 | 오류가 있을 때 대응 정보를 표시하면 됨 |
| 시트 이름·선택 개수의 별도 요약 카드 | 제거 | 같은 화면의 입력·선택과 중복 |
| 제목 아래 기능 소개 | 기본 없음 | 대상 제목과 행동으로 이해 가능 |
| 업로드 실패·미지원 선택 | 조건부 유지 | 사용자가 수정할 대상을 알아야 함 |
| 생성 시 외부 전송 안내 | 유지 | 자료 전달에 대한 판단에 영향 |
| 기존 케이스 교체 확인 | 유지 | 작업 결과를 잃을 수 있는 선택 |
| 내보내기 포함 범위 | 내보내기 시 유지 | 필터·후보 포함 여부 오해 방지 |
| 공유 화면 읽기 전용 | 후속 공유에서 유지 | 편집 가능 여부를 결정 |
| 사용자 입력·자료 속 문구 | 제품 문구와 구분 | 디자인 이미지 안의 원문까지 제품 안내로 취급하지 않음 |

## 11. 새 이미지 레퍼런스와 한계

이번 대화에서 내장 image_gen으로 생성했다. 이전 레퍼런스·기존 화면을 입력하지 않았다. 사용자 지적 후 수정본만 최종 산출물에 포함한다. 사용한 전체 프롬프트는 [image-prompts.md](image-prompts.md)에 보관한다.

- [플러그인: 선택·업로드·웹 이동](plugin-reference.png)
- [웹: 새 테스트 시트](generation-reference.png)
- [웹: 케이스 표와 상세 패널](editor-reference.png)

이미지는 배치·위계의 레퍼런스이며 실제 UI 코드·정밀 토큰 값·기능 동작 검증이 아니다. 샘플 프로젝트·이름·케이스 수·화면 내용은 가상 데이터다. 생성 도구가 만든 다음 세부 표현은 구현 기준으로 채택하지 않는다.

- 플러그인 시안의 큰 썸네일·여백은 실제 작은 창에서 목록 밀도를 확인하고 조정한다. 진행 수는 실제 관측 가능할 때만 쓴다. 이미지의 제목 위 숫자는 디자인 보드의 단계 구분이며 제품 UI가 아니다.
- 생성 시안은 `사용자 흐름`이 선택된 한 상태다. 이를 무조건 기본값으로 사용하지 않는다. `화면 연결 · 3개`도 실제 연결 수로만 표시한다.
- 편집 시안은 12개 중 일부 행을 보여주는 예시다. 연결된 프레임과 IA 연결은 서로 다른 대상이며 실제 상세 패널에 따로 제공한다.
- 생성 이미지의 보라색 음영·상태 배지 색과 버튼 채움은 토큰의 정확한 값이 아니다. 제품 구현은 theme.css의 의미 토큰을 기준으로 한다.
- 예시 기대 결과는 가상의 쇼핑몰 정책이다. 실제 자료에 근거가 없는 정책은 후보로 분리해야 한다.

## 12. 구현 순서와 완료 조건

### 제안하는 구현 순서

1. 프로젝트 탐색·시트 목록과 플러그인 업로드 흐름. 실제 Figma→웹 이동 검증.
2. 생성 준비·작업 상태·케이스 표·상세 패널. 빈 시트 경로와 자동 저장 함께 검증.
3. 후보 검토·기존 시트 교체·저장 충돌·XLSX. 데이터 보존과 포함 범위 검증.
4. 화면 목록·기본 양식의 맥락 정리. 파일 분석·흐름도는 현재 단계에 맞춰 별도 연결.
5. 공유 정책·배포 범위 결정 후 읽기 전용 공유.

실제 구현 전에는 이 설계에 포함되지 않은 작은 UI도 새 이미지 레퍼런스를 먼저 만든다. 이번 이미지를 모든 후속 UI의 사전 검토 완료로 취급하지 않는다. 현재 코드 열람 금지는 이번 작업 전체에 적용한다. 구현 단계의 코드 열람이 필요해지면 사용자 지시 범위를 먼저 정리해야 한다.

### 검증 시나리오

| 과제 | 관찰할 결과 |
| --- | --- |
| Frame·Section 혼합 및 중첩 선택 후 업로드 | 사용자에게 보인 대상과 실제 묶음이 일치하고 중복 업로드 없음 |
| 프로젝트 변경 후 업로드 | 성공 화면·웹 진입이 실제 업로드 프로젝트와 일치 |
| 업로드 완료 후 브라우저 이동 실패 | 업로드 성공은 유지되고 웹 이동만 다시 할 수 있음 |
| 설명만으로 생성 / 빈 시트 작성 | 자료 업로드나 IA 등록 없이 각 경로가 완료됨 |
| 생성 중 다른 시트 열기 | 대상만 잠기고 돌아와 상태를 확인할 수 있음 |
| 기존 시트 생성 실패 | 기존 케이스와 미저장 입력이 손실되지 않음 |
| 후보만 생성됨 | 케이스처럼 내보내지 않고 검토·추가 경로가 보임 |
| 긴 한국어 텍스트·IME·복붙 | 내용 누락·조기 제출 없이 편집 가능 |
| 저장 실패·충돌·이동 | 저장 성공을 거짓 표시하지 않고 입력 보존 |
| 검색 중 XLSX | 저장된 전체 케이스·현재 열 순서, 후보 제외 |
| 200% 확대·좁은 폭·키보드 | 주요 행동 접근, 표 스크롤, 패널 포커스 복귀 |
| 후속 공유 | 읽기 전용, 허용된 정보만 노출, 무효 링크에 내용 없음 |

사용성 검증은 처음 쓰는 사람에게 설명 없이 업로드→생성→후보 판단→내보내기 과제를 주고, 잘못된 프로젝트 선택·생성 범위 오해·후보 포함 오해가 생기는 지점을 기록한다. 시간·성공률 목표는 관측 전 임의 확정하지 않는다.

### 구현 전 사용자 판단이 필요한 사항

1. 실제 주요 사용자가 QA 작성자인지, 디자인 담당자인지와 주요 작업 기기. 현재 안은 작성자 중심 웹과 자료 전달용 플러그인을 가정했다.
2. 이번 탐색 구조·용어·생성 준비 방식의 채택. 현재 제품의 기능 계약을 바꾸지 않고 조작 흐름을 재배치하는 제안이다.
3. 공유를 시작할 시점과 접근·고정본/실시간·자료 포함·회수 정책. 구체적인 대안은 8절에 있다.

이 결정들이 남아 있어도 설계 산출물은 검토할 수 있다. 미정 사항을 제품 문서의 확정 사항으로 옮기거나 API를 변경하지 않는다.
