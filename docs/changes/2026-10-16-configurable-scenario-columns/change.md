## 확정된 요구사항

- 테스트 ID와 테스트 항목은 삭제할 수 없는 필수 열이다. 내부 UUID와 사용자에게 보이는 테스트 ID는 별도다.
- 그 밖의 열은 사용자가 구성한다. 사전 조건·수행 절차·예상 결과·우선순위도 제품이 강제하는 필드가 아니다.
- 사용자 열 형식은 텍스트, 선택, 체크박스, 태그다. 선택은 단일 항목, 태그는 여러 항목이다. 선택과 태그의 후보는 사용자가 설정하며 AI가 새 후보를 만들지 않는다.
- AI 입력과 결과 형식은 생성 대상 시나리오의 양식에서 만들어야 한다. 양식에 없는 업무 열을 생성하거나 숨겨 저장하지 않는다.
- 설정한 열의 이름과 형식이 표·상세 편집·확인 항목·미리보기·XLSX에 일관되게 적용되어야 한다.

## 전환 설계

- 프로젝트 기본 양식을 새 시나리오에 복사하는 기존 흐름을 유지한다. 복사 후 시나리오의 양식은 독립적이며, 기본 양식을 바꿔도 기존 시나리오를 덮어쓰지 않는다.
- 열 정의는 안정적인 UUID, 이름, 형식, 선택 항목, 선택적인 작성 기준을 가진다. 열 이름 변경으로 기존 값의 연결이 끊기지 않는다. 옵션도 UUID와 이름을 분리해 이름 변경 시 값을 보존한다.
- 케이스의 고정 업무 값은 ID와 제목이다. 사용자 값은 열 UUID를 키로 보관한다. 텍스트는 문자열, 선택은 옵션 UUID 또는 null, 체크박스는 boolean, 태그는 옵션 UUID 배열이다.
- 화면·Figma 자료·요구사항의 근거 연결은 별도 연결 데이터로 유지한다. 사용자에게 업무 열로 강제하지 않는다.
- 생성 직전의 시나리오 양식을 작업 snapshot으로 사용한다. AI는 열 이름·형식·작성 기준·허용 옵션을 받고 해당 열의 값만 반환한다. 필수 ID는 프로그램에서 부여한다.
- AI 출력은 저장 전에 제목, 열 ID, 값 형식, 선택 항목 소속, 태그 중복, 근거 참조를 검증한다. 정의하지 않은 열이나 옵션을 임의로 추가하지 않는다.
- 사용자가 개발 데이터 초기화를 명시적으로 허용했다. 구형 필드와 초안의 변환·호환 처리는 추가하지 않는다. 로컬 개발 데이터 초기화 후 새 스키마를 적용하고 브라우저 초안은 새 버전의 저장 키로 시작한다.
- 새 양식의 최소 구성은 ID와 제목이다. 예시 열이 필요해도 삭제 가능한 사용자 열이어야 한다.

## 구현과 검증 순서

1. 제품·구조 문서의 현재 계약을 갱신하고 과거 작업 기록은 당시 이력으로 보존한다.
2. DB·API·양식 검증·저장을 변경한다. 개발 데이터 초기화와 빈 DB에서의 마이그레이션 재현을 검증한다.
3. OpenAPI와 양쪽 앱 SDK를 재생성한다.
4. 이미지 레퍼런스를 기준으로 기존 열 설정 UI에 형식·옵션·작성 기준을 추가한다. 표·상세·확인 항목·미리보기·복붙·XLSX를 같은 열 정의에 맞춘다.
5. AI 결과 스키마와 검증을 양식에서 생성한다. 실제 외부 AI 호출은 수행 여부를 별도 기록한다.
6. 임의 양식으로 설정 → 생성 → 편집 → 저장 → 재조회 → 내보내기를 검증한다. 양식에 없는 우선순위·본문이 강제되지 않아야 한다.
7. 선택/태그의 목록 밖 값, 잘못된 boolean, 필수 열 삭제, 충돌과 실패 시 기존 값 보존을 회귀 검증한다. UX 문구 독립 검수와 정적 검사를 수행한다.

## 시안 대비 품질 보완 — 2026-10-16

사용자가 구현 캡처와 시안의 품질 차이를 지적했다. 앞선 대조는 기능 요소의 유무 위주였고, 중첩된 테두리·메타 정보 없는 목록·과도한 여백·팝업 잘림을 놓쳤다. 이를 완료 후 발견된 결함으로 기록한다.
