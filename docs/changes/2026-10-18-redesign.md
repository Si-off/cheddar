### 2단계 검증

아래 pnpm 명령에는 `--config.verifyDepsBeforeRun=false`를 추가했다. Node 24.12.0 환경에서 실행했으며 저장소 요구 버전(24.22.0 이상) 검증은 별도로 남는다. 자동 의존성 설치 검사에서는 엔진 불일치가 발생했다.

| 검증 | 결과 |
| --- | --- |
| `pnpm --filter @cheddar/api build` | 통과 |
| `pnpm --filter @cheddar/api typecheck` | 통과 |
| `pnpm exec biome check apps/api` | 통과 |
| `pnpm --filter @cheddar/api db:generate` | 27개 테이블, 새 기준 SQL 1개 생성 |

| `pnpm --filter @cheddar/api openapi:check` | 통과 |
| `pnpm test:api` | 6개 최상위 테스트 중 5 통과, 1 실패. TEST_DATABASE_URL 미설정으로 PostgreSQL 묶음의 실행 전 조건 실패 |
| `git diff --check`(이번 변경 범위) | 통과 |

통과한 테스트는 명세와 Swagger 스키마 검증, HTTP의 잘못된 로그인·초대·재설정 입력 400 응답, DTO null·권한·길이 검증, scrypt, 토큰 무작위성·해시, 프로젝트 없는 업로드 경로 저장과 경로 이탈 거부다. 린터가 요청 DTO를 type-only import로 바꾸면 런타임 검증 메타데이터가 사라지는 문제를 요청별 Swagger DTO 참조로 막았고 HTTP 검증으로 확인했다.

실제 PostgreSQL 묶음에는 기본 역할·CLI 부트스트랩, 상태별 로그인, 7일 토큰·재발급·단일 사용·용도 구분, 세션 폐기, 권한 합산·프로젝트 범위·전체만 권한 무시, 마지막 관리자 권한·할당·만료·비활성화와 동시 변경 보호, 필수 만료일과 최단 기본 기간, 링크 방문자 제약, 삭제 제한, 검색·필터, 소유권 이전, 운영 Secure 쿠키를 작성했다. 이 묶음과 실제 기준 마이그레이션 적용·관리자 생성의 성공은 아직 확인하지 못했다.

### 웹·후속 단계에 필요한 작업

- 웹 fetch client에 `credentials: "include"`를 적용하고 API와 SameSite 조건을 맞춘다. `GET /auth/me`의 permissions와 프로젝트 범위로 라우트·행동을 제어한다.
- 로그인, 초대·재설정 token 입력 화면, 계정·역할·소속 관리 화면과 새로운 상태·오류 처리를 연결한다. 초대·재설정 링크의 웹 경로는 아직 없다. 토큰 발급 응답을 링크로 조합해 직접 전달한다.
- 역할 할당은 `{ roleId, scope: "global" | "projects", projectIds }` 목록 전체를 보낸다. global은 빈 목록, projects는 1개 이상이다. expiresAt은 명시적으로 보내며 defaultExpiryDays는 초기값 제안에 사용한다.
- 링크 방문자 수정은 permissions만 보낸다. 활성화 후에도 만료일이 지났으면 만료 상태다. 비밀번호가 없는 계정은 초대됨으로 돌아가므로 링크를 재발급한다.
- 계정 관리만 가진 사용자의 역할·소속 선택 목록은 현 관리 API의 `role.manage` 경계와 함께 후속 화면에서 검토해야 한다. 현재 역할·소속 CRUD의 권한은 요청한 대로 유지했다.
- 3~7단계에서 생성 SDK를 다시 만들고 프로젝트·테스트 세트·공유·생성·플러그인 연결·WebSocket 권한 변경 전파를 구현한다. 스키마에 담은 후속 검증 조건은 구조 문서에 열거했다.
- 새 기준 전용 PostgreSQL 테스트 DB와 요구 Node 버전에서 API 테스트 및 잠금 파일 설치 검증을 완료한다. 전체 `pnpm check`와 웹 e2e는 이번 UI 병행 작업을 포함하므로 이 세션에서 실행하지 않았다.

### 3단계 결과

- 이전 웹 화면, 위젯, 엔티티, 디자인 프로토타입, 웹 legacy CSS를 지우고 FSD로 다시 만들었다. 웹 SDK를 새 명세로 다시 생성했다.
- 라우터: 공개 경로(/login, /invite, /password-reset), 로그인 경계(세션이 없으면 돌아갈 주소와 함께 로그인으로), 권한 경계(/admin과 하위 경로, 권한이 없으면 /no-access). 테스트 세트와 프로젝트는 4, 5단계 전까지 제목만 있는 임시 화면이다.
- 관리: 계정 목록(검색, 역할, 소속, 상태 필터), 계정 만들기와 초대 링크, 계정 상세(수정, 비활성화, 다시 활성화, 초대 다시 발급, 재설정 링크), 역할 목록과 편집(고정 역할 제약, 전체만 표시, 만료일 규칙), 소속 추가, 이름 변경, 삭제.
- 남은 것: 역할 할당의 프로젝트 범위 선택은 프로젝트 API(4단계)가 생기면 붙인다. 지금은 기존 프로젝트 범위 할당을 그대로 보여주고 유지만 한다. 소유 테스트 세트 넘기기 화면은 5단계.
- 검증: e2e 10건 통과(API 응답 합성), 관리 화면과 초대 화면을 실제 렌더링으로 확인. 실제 API와 DB로는 확인하지 못했다(테스트 DB 없음).
- UX 문구 검수 두 번: 비밀번호 12~128자(서버 조건), 목록 상한 100, 조회 실패는 토스트와 다시 시도, 링크 오류 구분, 활성 계정만 재설정 링크, 로그아웃 실패 알림, 링크 재발급 전 확인, 응답을 못 받았을 때 작업별 확인 방법 안내를 반영했다.
- 보안 검토: 로그인 후 돌아갈 주소는 같은 출처 경로만 받는다.
- API: 계정 관리 권한만 있어도 역할과 소속 목록을 읽을 수 있게 가드에 "여러 권한 중 하나"를 추가했다(계정을 만들 때 필요). 이 경로의 DB 테스트는 테스트 DB가 없어 추가하지 못했다.

### 4단계 결과
