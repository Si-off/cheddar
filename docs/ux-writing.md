# UX Writing & Product UI Policy

## 목적과 적용 범위

Cheddar는 사용자가 빠르게 업무를 파악하고 행동하는 도구다.
사용자에게 표시되는 모든 문구는 실제 사용자의 의문을 해결하거나 판단·행동을 도와야 한다.

최종 UI는 기능 명세서, 도움말 문서, 개발 보고서가 아니다.
사용자에게 필요한 정보를 정확하게 전달하고, 화면에서 이미 이해할 수 있는 내용은 반복하지 않는다.

이 정책은 웹, Figma 플러그인 UI, 공통 UI 컴포넌트와 디자인 미리보기·데모의 사용자 노출 문구에 적용한다.
제목, 레이블, 버튼, 보조 설명, 툴팁, 상태, 빈 화면, 오류 메시지, 접근성 레이블을 포함한다.

현재 작업에서 추가·변경한 문구와 그 영향을 받는 주변 문구를 검수한다.
삭제한 문구는 필수 정보나 접근성 이름을 함께 제거하지 않았는지 확인한다.
별도 요청 없이 기존 제품 전체의 문구를 정리하거나 기능·화면 구조를 변경하지 않는다.

## 1. 문구 생성과 화면 구성

- 제품이 작성하는 UI 문구에서는 `·`를 사용하지 않는다. 사용자 작성 이름, 가져온 데이터, 원본 콘텐츠는 보존한다. 쉼표나 슬래시로 치환해 같은 나열을 유지하지 않고, 불필요한 정보는 제거하며 필요한 정보는 역할에 맞는 위치와 요소로 분리한다.
- 삭제 → 화면 구성으로 해결 → 필요한 문구 작성 순서로 판단한다. 정보의 관계는 그룹·배치·위계로, 조작 방법은 기존 컨트롤과 상태로 전달한다. 설명을 삭제한 자리에 배지·툴팁·아이콘을 자동으로 추가하지 않는다. 텍스트는 현재 식별하거나 결정해야 하는 정보만 남기고, 색이나 아이콘만으로 필수 의미를 전달하지 않는다.
- 내부 처리 사실만으로 안내를 만들지 않는다. AI 사용·전송·모킹·저장 기술·구현 한계 자체는 충분한 근거가 아니다. 유지 근거는 확정된 요구사항 또는 그 자리에서 사용자가 내려야 할 구체적인 결정이어야 한다. “오해할 수 있다”, “안전하게 알려준다”만으로 필수 안내나 새로운 고지 의무를 만들지 않는다. 실제 입력 손실, 교체 범위, 오류 복구와 접근성 정보는 보존한다.

## 2. 제목과 레이블

- 제목·탭·메뉴·필드명·버튼 등 UI 레이블은 명사형 또는 동사형으로 작성한다. 설명문·대화체 표현은 사용하지 않으며, 같은 역할의 레이블은 표현 형식을 일관되게 유지한다.
- 이 표현 형식 제한은 오류·상태·안내 문장에는 적용하지 않는다.
- 기능명은 대상과 실제 행동이 드러나는 짧고 쉬운 단어로 정한다.
- 익숙한 업무·전문 용어는 불필요하게 순화하지 않는다.
- 같은 의미에는 같은 용어를 쓰고, 다른 대상과 행동은 구분한다.
- 개발 변수명, DB 개념, 기획서 표현은 사용자의 업무 언어로 바꾼다.
- 제목이나 레이블만으로 이해할 수 있으면 보조 설명을 추가하지 않는다.
- 상태 메시지는 현재 상황을 전달한다.
- 오류 메시지는 발생한 문제와 사용자가 실행할 수 있는 다음 행동을 전달한다.
- 저장 여부, 복구 가능성, 재시도 가능성은 실제 동작으로 확인된 내용만 안내한다.

## 3. 툴팁 생성 기준

툴팁은 기본적으로 만들지 않는다.
다음 조건을 모두 충족할 때만 추가한다.

1. 실제 사용자가 해당 요소의 의미를 혼동할 가능성이 있다.
2. 레이블을 수정하는 것만으로는 혼동을 해결하기 어렵다.
3. 짧은 보충 정보로 혼동을 해결할 수 있다.
4. 툴팁이 없어도 핵심 작업을 수행할 수 있다.

추가한 툴팁은 다음 기준을 따른다.

- 한 가지 의문에만 답한다.
- 기본적으로 한 문장으로 작성한다.
- 문단, 목록, 기능 소개, 조작 방법 나열을 피한다.
- 이미 화면에 보이는 정보를 반복하지 않는다.
- 중요한 작업 조건, 권한, 제한, 데이터 의미는 항상 보이는 적절한 위치에 표시한다.
- 툴팁의 존재 이유를 사용자의 구체적인 의문으로 설명할 수 있어야 한다.

아이콘 버튼의 접근성 이름은 툴팁과 별도로 판단한다.
툴팁을 삭제하더라도 버튼의 목적을 전달하는 접근성 레이블을 유지한다.

## 4. 피할 문구 패턴

다음 표현은 사용자에게 주는 구체적인 정보가 있을 때만 사용한다.

- "한곳에 모았습니다"
- "탭을 선택하면 자세한 설명이 나옵니다"
- "이 영역에서는 ... 확인할 수 있습니다"
- "같은 항목은 중복으로 표시하지 않습니다"
- "사용자 편의를 위해 ... 제공됩니다"

기능 동작을 소개하기 위한 불필요한 장문, 개발자에게 보고하는 듯한 설명,
화면의 구성이나 구현 의도를 설명하는 메타 발언도 같은 기준으로 판단한다.

표현이 목록에 있다는 이유만으로 기계적으로 삭제하지 않는다.
데이터의 포함 범위, 누락, 집계 방식이 판단에 영향을 주는 경우에는
사용자에게 필요한 의미를 정확하고 간결하게 전달한다.

## 5. 문구 판단 기준

- [문구 생성과 화면 구성](#1-문구-생성과-화면-구성)에 따라 필요성을 판단하고, 필요한 정보는 해당 행동의 위치와 시점에 제공한다.
- 안내하는 행동은 현재 제공된 화면·권한·상태에서 수행 가능해야 한다. 저장 여부·재시도 안전성은 실제 처리 경로를 근거로 판단한다.

다음 예시는 문구 판단을 위한 것이며 새로운 기능이나 제품 요구사항을 정의하지 않는다.

| 상황 | 기존 문구 | 권장 처리 | 이유 |
| --- | --- | --- | --- |
| 테스트 케이스 목록 제목 | 이 영역에서는 테스트 케이스를 확인할 수 있습니다 | 테스트 케이스 | 제목으로 대상을 직접 명명한다. |
| 내보내기 버튼의 보조 설명 | 사용자 편의를 위해 XLSX 내보내기를 제공합니다 | 삭제하고 버튼에 XLSX 내보내기 사용 | 버튼이 행동을 충분히 설명한다. |
| 검색 입력의 툴팁 | 검색어를 입력하면 검색할 수 있습니다 | 삭제 | 입력의 목적을 반복한다. 필요한 검색 범위 정보는 별도로 판단한다. |
| 공유 화면의 권한 안내 | 읽기 전용 | 유지 | 편집 가능 여부는 사용자의 행동에 영향을 준다. |
| 빈 목록 안내 | 현재 이 영역에는 데이터가 존재하지 않습니다 | 테스트 케이스가 없습니다 | 현재 상태를 구체적인 업무 용어로 전달한다. |

## 6. 코드 기반 검수

[검수 에이전트 정의](../.codex/agents/ux-writing-review.toml)는 입력·확인 범위·결과·재검수 방법을, [작업 절차](workflow.md#ux-문구-검수-흐름)는 독립 검수 호출과 결과 반영을 관리한다. 이 정책은 문구 판단 기준이며, 실행 화면 확인은 문구 검수의 필수 조건이 아니다.

화면 구성이 문제인 경우 문장 수정만으로 해결됐다고 판정하지 않는다. 구현 담당자가 해당 영역을 수정하고 실제 화면을 확인한다.
