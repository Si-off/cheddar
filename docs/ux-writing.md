# UX Writing & Product UI Policy

## 목적과 적용 범위

Cheddar는 사용자가 빠르게 업무를 파악하고 행동하는 도구다.
사용자에게 표시되는 모든 문구는 실제 사용자의 의문을 해결하거나 판단·행동을 도와야 한다.

최종 UI는 기능 명세서, 도움말 문서, 개발 보고서가 아니다.
사용자에게 필요한 정보를 정확하게 전달하고, 화면에서 이미 이해할 수 있는 내용은 반복하지 않는다.

이 정책은 웹, Figma 플러그인 UI, 공통 UI 컴포넌트와 디자인 미리보기·데모의 사용자 노출 문구에 적용한다.
제목, 레이블, 버튼, 보조 설명, 툴팁, 상태, 빈 화면, 오류 메시지, 접근성 레이블을 포함한다.

현재 작업에서 추가·변경한 문구와 그 영향을 받는 주변 문구를 검수한다.
삭제한 문구는 필수 정보나 접근성 이름을 함께 제거하지 않았는지 확인한다.
별도 요청 없이 기존 제품 전체의 문구를 정리하거나 기능·화면 구조를 변경하지 않는다.

## 1. 문구 생성 조건과 내부 정보의 분리

- UI 문구는 대상 식별, 행동 선택, 상태 이해, 결과 해석에 필요한 역할이 확인된 경우에만 추가한다. 화면을 풍성하게 보이게 하거나 산출물의 완성도를 설명하기 위해 추가하지 않는다.
- 디자인 방향과 톤앤매너는 형태, 배치, 색상, 움직임으로 구현한다. 이를 설명하는 문장을 UI 문구로 자동 생성하지 않는다.
- 제목 아래 설명, 섹션 소개, 배지, 보조 정보 영역은 기본으로 구성하지 않는다. 전달할 내용의 필요성을 먼저 확인한 뒤 적절한 위치와 표현을 정한다.
- 사실인 정보도 현재 위치에서 사용자의 판단이나 행동에 영향을 주는 경우에만 표시한다.
- 요구사항에 없는 브랜드 표현이나 기능 소개를 임의로 작성하지 않는다. 해당 문구 작성이 요청 범위에 포함된 경우에만 다룬다.
- 데이터 조회 범위, 중복 제거, 우선순위, 내부 상태 전이, 렌더링 정책, 예외 처리, 테스트 조건은 내부 명세로 관리한다.
- 요구사항의 구현 설명을 그대로 UI에 복사하지 않는다.
- 사용자가 기술적 작동 원리를 알아야 판단하거나 행동할 수 있는 경우, 해당 위치에서 필요한 범위만 설명한다.
- 설명의 양은 구현의 복잡성이 아니라 사용자의 정보 필요성을 기준으로 정한다.
- 데이터의 포함 범위, 누락, 집계 방식이 사용자 판단에 중대한 영향을 주면 필요한 안내를 유지한다.

## 2. 제목과 레이블

- 사용자가 익숙한 업무 용어를 우선한다.
- 사용자가 무엇을 보거나 실행할 수 있는지 구체적으로 명명한다.
- 같은 의미에는 같은 용어를 사용한다.
- 개발 변수명, DB 개념, 기획서 표현은 사용자의 업무 언어로 바꾼다.
- 의미 없이 친절하거나 대화체인 표현을 덧붙이지 않는다.
- 제목이나 레이블만으로 이해할 수 있으면 보조 설명을 추가하지 않는다.
- 상태 메시지는 현재 상황을 전달한다.
- 오류 메시지는 발생한 문제와 사용자가 실행할 수 있는 다음 행동을 전달한다.
- 저장 여부, 복구 가능성, 재시도 가능성은 실제 동작으로 확인된 내용만 안내한다.

## 3. 툴팁 생성 기준

툴팁은 기본적으로 만들지 않는다.
다음 조건을 모두 충족할 때만 추가한다.

1. 실제 사용자가 해당 요소의 의미를 혼동할 가능성이 있다.
2. 레이블을 수정하는 것만으로는 혼동을 해결하기 어렵다.
3. 짧은 보충 정보로 혼동을 해결할 수 있다.
4. 툴팁이 없어도 핵심 작업을 수행할 수 있다.

추가한 툴팁은 다음 기준을 따른다.

- 한 가지 의문에만 답한다.
- 기본적으로 한 문장으로 작성한다.
- 문단, 목록, 기능 소개, 조작 방법 나열을 피한다.
- 이미 화면에 보이는 정보를 반복하지 않는다.
- 중요한 작업 조건, 권한, 제한, 데이터 의미는 항상 보이는 적절한 위치에 표시한다.
- 툴팁의 존재 이유를 사용자의 구체적인 의문으로 설명할 수 있어야 한다.

아이콘 버튼의 접근성 이름은 툴팁과 별도로 판단한다.
툴팁을 삭제하더라도 버튼의 목적을 전달하는 접근성 레이블을 유지한다.

## 4. 피할 문구 패턴

다음 표현은 사용자에게 주는 구체적인 정보가 있을 때만 사용한다.

- "한곳에 모았습니다"
- "탭을 선택하면 자세한 설명이 나옵니다"
- "이 영역에서는 ... 확인할 수 있습니다"
- "같은 항목은 중복으로 표시하지 않습니다"
- "사용자 편의를 위해 ... 제공됩니다"

기능 동작을 소개하기 위한 불필요한 장문, 개발자에게 보고하는 듯한 설명,
화면의 구성이나 구현 의도를 설명하는 메타 발언도 같은 기준으로 판단한다.

표현이 목록에 있다는 이유만으로 기계적으로 삭제하지 않는다.
데이터의 포함 범위, 누락, 집계 방식이 판단에 영향을 주는 경우에는
사용자에게 필요한 의미를 정확하고 간결하게 전달한다.

## 5. 문구 작성과 판단 절차

문구를 추가·변경·삭제할 때 다음을 확인한다.

A. 대상 식별, 행동 선택, 상태 이해, 결과 해석에 필요한 정보인가?
B. 화면의 데이터나 레이블만으로 이미 이해할 수 있는가?
C. 사용자의 업무 언어로 작성했는가?
D. 삭제하면 사용자가 무엇을 식별하거나 결정하거나 실행하기 어려워지는가?
E. 실제 기능, 표시 조건, 데이터 의미와 일치하는가? 안내하는 행동을 현재 제공된 화면·권한·상태에서 수행할 수 있는가?
F. 필요한 정보라도 지금 이 위치와 시점에 표시해야 하는가?

다음 순서로 판단한다.

1. 실제 기능과 데이터 의미를 확인한다. 행동 안내는 도착 화면과 처리 경로를 확인하며 저장 여부·재시도 안전성을 추측하지 않는다.
2. 문구를 삭제했을 때 사용자가 겪을 구체적인 어려움으로 정보의 필요성을 확인한다.
3. 필요성과 별도로 표시 위치와 시점의 적절성을 판단한다.
4. 레이블을 명확하게 바꾸는 것으로 해결할 수 있는지 확인한다.
5. 필요한 정보만 남기고 중복 설명을 삭제하거나 축약한다.
6. 필수 조건, 오류 대응 정보와 접근성 이름이 유지되는지 확인한다.

A의 필요성을 D의 구체적인 어려움으로 설명할 수 없으면 삭제 대상으로 판단한다.
"분위기를 전달한다", "이해를 돕는다", "검토 화면에 유용하다" 같은 포괄적인 이유만으로 유지하지 않는다.
B가 맞으면 같은 내용을 설명하는 도움말을 추가하지 않는다.
레이블이 불명확하다면 도움말보다 레이블 수정을 우선한다.
F가 아니라면 필요한 정보는 유지하되 적절한 위치나 표시 시점으로 조정한다.

시안·데모도 현재 작업의 목적과 대상 사용자를 기준으로 판단한다. 모킹·저장 방식·연동 여부 같은 제작 사정을 화면 안내로 자동 전환하지 않는다. 사용자의 입력·전송·교체·손실 판단에 필요한 정보는 해당 행동이 일어나는 위치와 시점에 제공한다.

다음 예시는 문구 판단을 위한 것이며 새로운 기능이나 제품 요구사항을 정의하지 않는다.

| 상황 | 기존 문구 | 권장 처리 | 이유 |
| --- | --- | --- | --- |
| 테스트 케이스 목록 제목 | 이 영역에서는 테스트 케이스를 확인할 수 있습니다 | 테스트 케이스 | 제목으로 대상을 직접 명명한다. |
| 내보내기 버튼의 보조 설명 | 사용자 편의를 위해 XLSX 내보내기를 제공합니다 | 삭제하고 버튼에 XLSX 내보내기 사용 | 버튼이 행동을 충분히 설명한다. |
| 검색 입력의 툴팁 | 검색어를 입력하면 검색할 수 있습니다 | 삭제 | 입력의 목적을 반복한다. 필요한 검색 범위 정보는 별도로 판단한다. |
| 공유 화면의 권한 안내 | 읽기 전용 | 유지 | 편집 가능 여부는 사용자의 행동에 영향을 준다. |
| 빈 목록 안내 | 현재 이 영역에는 데이터가 존재하지 않습니다 | 테스트 케이스가 없습니다 | 현재 상태를 구체적인 업무 용어로 전달한다. |

## 6. 코드 기반 검수

UX 문구 검수는 코드와 관련 요구사항을 읽고 판단하는 방식으로 수행한다.
실제 브라우저나 Figma 실행 화면 확인은 이 검수의 필수 조건이 아니다.

검수 입력·코드 확인 절차·결과 형식은 [검수 에이전트 정의](../.codex/agents/ux-writing-review.toml)를, 호출과 결과 반영은 [작업 절차](workflow.md#ux-문구-검수-흐름)를 따른다. 판단에는 이 문서의 필요성·실행 가능성·표시 시점·접근성 기준을 적용한다.

코드로 확인하지 못한 표시 상태나 실제 동작은 확인했다고 보고하지 않는다.
실행 화면이나 미정인 제품 요구사항이 있어야 판단할 수 있는 항목은
필요한 근거와 함께 미확인 사항으로 남긴다.

이 검수는 UX 문구에 대한 검수다.
기능, 레이아웃, 상호작용 등 다른 검증의 범위는 해당 작업의 완료 조건을 따른다.

## 7. 완료 기준과 보고

다음 사항을 확인한다.

- 현재 작업의 신규·변경 문구를 검수했다.
- 문구의 필요성과 표시 위치·시점의 적절성을 각각 확인했다.
- 삭제한 문구에 필수 정보나 접근성 이름이 포함되지 않았는지 확인했다.
- 추가하거나 변경한 툴팁은 생성 기준을 모두 충족한다.
- 불필요한 툴팁과 중복 설명을 제거했다.
- 제목, 버튼, 상태, 빈 화면, 오류 메시지, 접근성 레이블을 검토했다.
- 문구를 삭제하거나 축약하면서 필수 정보와 접근성을 잃지 않았다.
- 검수 지적의 반영 결과와 필요한 재검수 결과를 확인했다.
- 미반영 사유와 미확인 사항을 기록했다.

완료 보고의 UX 문구 검수 항목에는 다음을 간결하게 기록한다.

- 코드 기반 검수 범위와 결과
- 주요 제거·축약 문구와 이유
- 필수 정보로 유지한 주요 문구
- 남은 미확인 사항 또는 검수 미수행 이유

변경하거나 유지한 모든 문구를 나열할 필요는 없다.
실제 화면을 확인하지 않았다면 코드 기반 검수 결과로 보고한다.
개발 설명은 사용자 UI에 넣지 않고 작업 보고에 필요한 범위로 기록한다.
