# 작업 절차

## 공통 작업 원칙

제품·구조 문서는 합의된 계약이며, 결정 기록은 선택 이유를 설명한다. 개별 브랜치의 구현 상태와 진행 이력은 작업 기록에 둔다. 미정인 제품 범위·기술 선택은 사용자 결정 후 현재 문서에 반영한다.

## 1. 작업 시작

`AGENTS.md`에서 현재 작업에 해당하는 문서만 읽는다. 알려진 관련 브랜치·worktree의 구현을 확인하지 않고 현재 체크아웃만으로 프로젝트 전체를 미구현으로 단정하지 않는다.

폴더와 산출물 경로는 [프로젝트 구조](architecture.md#파일-생성과-폴더-변경)의 승인 범위와 [임시 파일 정책](architecture.md#임시-파일과-도구-산출물)을 따른다.

## 2. 작업 규모와 기록

- 오타·문구 등 작고 명확한 수정은 요청과 결과 보고로 충분하다. 별도 계획 문서를 만들지 않는다.
- 기능 추가·동작 변경·여러 세션에 걸친 작업은 [작업 기록 안내](changes/README.md)에 따라 기존 `change.md`에 계획·검증·인계를 모은다. 중요한 제품·구조 선택의 배경은 필요할 때 결정 기록으로 연결한다.

## 3. 설계와 실행

UIUX를 구현·수정할 때는 코드 변경 전에 이미지 생성 도구로 레퍼런스 이미지를 먼저 생성해 사용자에게 보여주고, 이를 기준으로 작업한다. 구현 후에는 실제 화면을 레퍼런스와 대조한다.

시안의 모킹 데이터·제작 방식은 확정된 제품 요구사항이 아니다. 사용자가 요청한 대상과 결과를 기준으로 구현한다.

## 4. 검증

명령·환경·검증 범위는 [README의 검증 안내](../README.md#검증과-api-코드-생성)에 있다. `pnpm check`는 정적 검사·빌드이며 동작 테스트나 실제 외부 서비스 연동 성공의 근거가 아니다. 외부 서비스 변경은 대표 입력 크기와 제공자별 요청·응답·오류 계약을 확인하고, 실제 호출 여부를 결과에 남긴다.

### 테스트 작성 기준

사용자 동작·업무 규칙·오류·회귀를 중심으로 검증한다. 모든 함수·분기나 커버리지 수치를 위한 테스트, CSS·내부 DOM·호출 순서만 고정하는 테스트는 작성하지 않는다. 접근성·표시 조건 등 기능 요구사항을 확인하는 검증은 보존한다.

### UX 문구 검수 흐름

사용자 노출 문구·툴팁의 추가·변경·삭제 또는 의미에 영향을 주는 표시 조건 변경에 적용한다.

1. 한 기능의 문구와 표시 조건이 안정되면 [검수 에이전트](../.codex/agents/ux-writing-review.toml)를 독립 컨텍스트로 호출한다. 목적·대상 사용자·관련 결정과 요구사항·diff 기준·대상 경로·관련 문서를 전달한다. 시안은 검토할 경험과 실제 연동·저장 범위를 포함한다.
2. 확인된 위반을 반영하거나 근거 있는 미반영 이유를 남긴다. 선택 의견은 완료를 막지 않으며 제품 결정이 필요한 사항은 사용자에게 확인한다.
3. 수정 후에는 변경된 범위와 미해결 사항만 재검수한다. 결과·미반영 이유·미확인 사항은 기존 작업 기록 또는 완료 보고에 한 번 남긴다.

검수는 [UX 정책](ux-writing.md)에 따른 코드 기반 검수이며 실행 화면 확인을 필수로 요구하지 않는다. 지정 에이전트·모델·effort를 사용할 수 없으면 미수행 사유를 보고하고 자체 검수나 다른 모델로 대체하지 않는다.

## 5. 커밋과 푸시

사용자는 `Si-off/cheddar` 저장소의 현재 작업 브랜치에 에이전트 자신의 작업을 커밋하고 일반 푸시하는 것을 상시 승인했다. 새 작업 브랜치의 최초 푸시도 포함하며 건별 승인을 요청하지 않는다. 사용자 보류 지시가 있으면 따르고, 다른 작업의 변경이나 무관한 미푸시 커밋은 포함하지 않는다.

강제 푸시·기존 커밋의 수정/합치기/이력 재작성·원격 브랜치 삭제·PR 생성·병합·배포는 별도로 승인된 범위에서만 수행한다. 푸시가 배포를 유발하는 경우에도 배포 승인 범위가 필요하다.

도구의 자동 승인 검토에는 실제 사용자 승인과 원격·브랜치·동작의 근거를 전달한다. 이 상시 승인은 도구·저장소의 실행 제한을 해제하지 않는다.

## 6. 완료와 인계

검증 근거는 기존 작업 기록 또는 완료 보고 한곳에 남긴다. 인계가 필요하면 작업 경로·브랜치와 남은 일·검증·승인 범위를 기존 `change.md`에 갱신한다.

적용 후 한 채팅 개발 작업 10건의 관찰은 [작업 기록 안내](changes/README.md#개선-효과-관찰)를 따른다.

## 7. 프로젝트 지식 갱신

제품·구조의 확정된 변경은 현재 문서에, 진행 메모·임시 예외는 해당 작업 기록에 둔다.

### 지침 변경 보호

`AGENTS.md`·대체 지침·에이전트 설정·스킬·Hook·허용 폴더·이 보호 정책의 변경은 경로·내용·이유를 알리고 명시적 승인을 받는다. 사용자가 같은 변경을 명시적으로 요청했다면 고지 후 진행하며 다시 승인받지 않는다. 일반 기능 구현·오류 수정·문서 정리 요청을 지침 변경 승인으로 확대하지 않는다. 사용자 전역 지침·설정 변경도 별도 승인 범위다.

변경한 지침 파일과 요지는 완료 보고에 남긴다. 지침은 도구·CI·파일시스템의 강제 제한과 구분한다.
