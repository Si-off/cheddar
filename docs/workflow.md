# 작업 절차

이 문서는 세션이 바뀌어도 유지할 작업 방식이다. 개별 작업의 목표·계획·진행 상황·승인은 해당 작업에만 속한다.

## 공통 작업 원칙

특정 채팅의 기억이나 개인 설정을 프로젝트의 기준으로 삼지 않는다. 현재 사용자의 명시적인 지시를 우선하며, 기존 코드·문서와 충돌하면 그 차이를 설명한다.

- 확정 사항, 미정 사항, 제안을 구분한다. 문서에 `미정`인 제품 내용이나 기술 스택을 임의로 확정하지 않는다.
- 새로운 기능의 범위나 중요한 설계 선택이 필요하면 선택지·영향·추천안을 제시하고 사용자의 결정을 반영한다.
- 요청 범위와 기존 변경을 보존한다. 관련 없는 정리·리팩터링·의존성 변경을 섞지 않는다.
- 현재 동작과 구조의 기준은 제품·구조 문서이며, 결정 기록은 선택 이유를 설명한다. 문서와 실제 코드가 다르면 차이를 확인하고 필요한 결정을 요청한다.
- 확정된 동작·구조를 변경하면 관련 현재 문서도 함께 갱신한다.

## 1. 작업 시작

현재 요청의 목적, 범위, 완료 조건과 실행 범위를 파악한다. 기존 코드와 Git 상태를 확인하고 작업 대상 경로의 지침을 적용한다. 제품이나 구조를 판단해야 할 때만 관련 현재 문서를 읽는다.

수정할 경로에 추가 `AGENTS.md`가 있는지 확인하고 해당 범위의 지침을 적용한다. 루트에서 시작한 세션이 모든 하위 지침을 자동으로 읽는다고 가정하지 않는다. 모든 문서나 과거 작업을 매번 읽지 않고 현재 작업에 필요한 문서만 선택한다. 같은 작업 중에 이미 읽은 절차는 변경된 경우에만 다시 읽는다.

커밋·푸시 권한과 절차는 [커밋과 푸시](#5-커밋과-푸시)를 따른다.

폴더 생성이나 도구 실행 전에 `architecture.md`의 허용된 구조와 산출물 경로를 확인한다. 저장소 안에 임시 파일을 만들지 않도록 출력·캐시 경로를 정한다. 새 폴더나 예외가 필요하면 경로·목적·영향을 먼저 제시하고 승인받는다. 이미 승인된 경로와 범위는 반복 승인받지 않는다.

## 2. 작업 규모와 기록

| 작업 | 기록과 계획 |
| --- | --- |
| 오타·문구 등 작고 명확한 수정 | 요청과 결과 보고로 충분하며, PR을 만들면 설명에 기록 |
| 기능 추가·동작 변경·여러 세션에 걸친 작업 | `docs/changes/<change-id>/change.md` 사용 |
| 중요한 제품·구조 선택 | 선택지·영향·추천을 제시하고 결정 후 현재 문서 갱신; 필요한 경우 결정 기록 추가 |

단순 수정에 별도 계획 승인과 문서 묶음을 강제하지 않는다. 문서 양은 변경 범위와 검토 필요성에 맞춘다. 기획 내용이 커지면 작업 폴더 안에서 의도·요구사항·계획을 별도 파일로 분리하고 `change.md`에서 연결한다.

## 3. 설계와 실행

새로운 기능의 범위나 중요한 선택이 미정이면 구현 전에 사용자가 판단할 수 있는 제안을 만든다. 계획에는 영향 범위, 작업 순서, 확인 가능한 완료 조건, 검증 방법을 포함한다.

- 승인된 범위에서는 구현·관련 검증·발견된 문제 수정을 이어서 진행한다. 같은 범위에 대해 반복 승인을 요구하지 않는다.
- 범위 확대나 새로운 중요한 결정이 필요하면 이유와 영향을 설명한다. 기존 승인 범위를 임의로 넓히지 않는다.

사소한 구현 선택마다 승인을 반복하지 않는다.

작업 문서에 기록한 승인 정보는 실제 지시나 승인 기록을 설명하기 위한 것이다. 에이전트가 상태값을 바꾸는 행위는 승인을 만들지 않는다. 승인된 대상이나 범위가 달라졌다면 이전 승인을 그대로 적용하지 않는다.

## 4. 검증

- 변경된 동작과 영향을 받는 인접 동작에 맞는 검증을 선택한다.
- 버그 수정은 가능하면 수정 전에 재현하고, 필요한 회귀 검증을 추가한다.
- UI의 기능·레이아웃·상호작용 변경은 실행 결과를 확인할 수 있는 환경에서 실제 화면과 동작을 확인한다.
- UX 문구는 [UX 문구 정책](ux-writing.md)에 따라 코드 기반으로 검수한다. 문구 검수 자체에 실제 브라우저나 Figma 실행 화면 확인을 필수로 요구하지 않는다.
- 테스트를 통과시키기 위해 요구사항과 무관하게 검증을 삭제·건너뛰기·완화하지 않는다. 정당한 테스트 변경은 이유를 설명한다.
- 명령, 결과, 실행 환경 등 검토에 필요한 근거를 남긴다. 긴 원본 로그는 검증 결과 링크로 연결할 수 있다.
- 실행하지 못한 검증을 성공으로 표현하지 않는다. 검사 수단이 아직 없다면 검증 수단 미정 또는 미구성으로 기록한다.

현재 기본 검증은 루트에서 `pnpm lint`, `pnpm typecheck`, `pnpm build`를 실행한다. `pnpm check`로 세 검사를 순서대로 실행할 수 있다. 설치·앱 실행·API 코드 생성의 환경변수와 경로는 [README](../README.md)를 따른다. 실제 API 명세·Figma ID가 필요한 검증은 해당 값이 준비된 뒤 별도로 수행한다. 테스트 프레임워크와 CI는 아직 미정이다.

### 테스트 작성 기준

- 테스트는 사용자에게 의미 있는 동작, 중요한 업무 규칙, 오류 처리와 실제 버그의 재발 방지를 중심으로 작성한다.
- 모든 함수·컴포넌트·분기에 일률적으로 테스트를 추가하지 않는다. 단순 값 전달, 상수 반환, 얇은 래퍼 등 독립적인 실패 위험이 낮은 코드는 이를 사용하는 동작의 테스트로 충분하면 별도 테스트를 생략한다.
- UI 테스트는 사용자 조작과 관찰 가능한 결과를 검증한다. CSS 클래스명, 색상, 간격, 크기, 장식 요소, 내부 DOM 구조 등 구현·표현 세부사항만 고정하는 테스트는 작성하지 않는다.
- 접근성, 표시·숨김, 입력·선택 상태, 스크롤·확대 등 기능 요구사항을 검증하는 데 필요한 경우에는 해당 속성이나 시각적 상태를 확인할 수 있다.
- 내부 함수 호출 순서나 상태 구조보다 외부에서 관찰 가능한 결과를 검증한다. 같은 동작을 여러 계층에서 중복 검증하려면 서로 다른 실패 위험을 다뤄야 한다.
- 테스트 수나 커버리지 수치를 높이기 위한 테스트는 추가하지 않는다. 각 테스트가 발견할 수 있는 오류를 설명할 수 있는 범위로 작성한다.
- 기존 테스트를 정리할 때는 불필요한 검증만 제거하고, 동작·접근성·오류 처리에 대한 검증은 보존한다.

### UX 문구 검수 흐름

사용자 노출 문구·툴팁을 추가·변경·삭제하거나 문구의 의미에 영향을 주는 표시 조건을 변경했다면 다음 흐름을 따른다.

1. 메인 에이전트가 구현을 마친 뒤 검수할 diff 기준과 대상 경로를 특정한다.
2. [UX 문구 검수 에이전트](../.codex/agents/ux-writing-review.toml)를 구현 대화 전체를 상속하지 않는 독립된 컨텍스트로 호출한다. 현재 작업의 목적, 관련 사용자 요구사항, diff 기준, 대상 경로와 관련 문서 위치를 전달한다.
3. 검수 에이전트가 자신의 정의에 있는 검수 절차와 결과 형식에 따라 수행한 결과를 기다린다. 메인 에이전트는 상세 검수 절차를 읽을 필요 없이 입력 전달과 결과 반영을 맡으며, 자체 검수로 대체하지 않는다.
4. 메인 에이전트가 지적 사항을 반영하거나 코드·요구사항·정책에 근거한 미반영 이유를 남긴다. 새로운 제품 결정이 필요하면 사용자의 결정을 받는다.
5. 검수 후 문구나 관련 표시 조건을 수정했다면 해당 범위의 재검수를 요청한다. 새로운 변경이나 미해결 문제가 없다면 동일한 검수를 반복하지 않는다.
6. 완료 보고에 정책의 완료 기준에 따른 검수 범위·결과·미확인 사항을 기록한다.

문구나 그 의미에 영향을 주는 표시 조건을 변경하지 않는 작업에는 별도 UX 문구 검수를 요구하지 않는다.
지정 에이전트나 지정된 모델·effort를 사용할 수 없으면 검수 미수행과 이유를 보고한다. 다른 모델이나 메인 에이전트 검수로 임의 대체하지 않는다.

검수 에이전트의 읽기 전용 동작은 에이전트 정의의 지침이다. 별도의 파일시스템 접근 제한을 구성한 것으로 표현하지 않는다.

## 5. 커밋과 푸시

- 작업을 수행한 에이전트는 자신이 만든 변경을 검토·검증한 뒤 의미 있는 작은 단위로 커밋하고, 현재 작업 브랜치에 일반 푸시한다. 커밋·푸시는 기본적으로 허용되며 매번 별도 승인을 요구하지 않는다.
- 사용자가 커밋·푸시 보류나 검토 우선을 명시하면 그 지시를 따른다. 다른 사용자·에이전트의 변경이나 무관한 미푸시 커밋을 함께 반영하지 않는다.
- PR 생성·병합·배포는 현재 작업에서 별도로 승인된 범위를 따른다. 자율 커밋·푸시 권한은 폴더 구조나 지침 변경의 사전 승인 절차를 생략할 권한이 아니다.

- 작업한 에이전트가 하나의 목적을 완성하는 작은 변경 단위로 커밋한다. 파일 개수만으로 쪼개지 않고 관련 코드·테스트·문서를 함께 묶는다. 독립적인 수정이나 리팩터링은 분리한다.
- 커밋 전에 diff와 관련 검증 결과를 확인하고 자신의 변경만 명시적으로 스테이징한다. 같은 파일에 다른 작업의 변경이 섞여 있으면 해당 변경을 보존하고 자신의 부분만 분리한다.
- 의미 있는 단위의 커밋과 검증이 끝나면 현재 작업 브랜치로 일반 푸시한다. 작업 종료까지 불필요하게 모든 변경을 모아 두지 않는다. 사용자의 보류·검토 우선 지시는 따른다.
- 푸시 전에 원격 URL, 대상 브랜치, 원격에 추가될 커밋 목록을 확인하고 저장소 보호 규칙을 따른다. 다른 작업의 미푸시 커밋이 섞이거나 대상이 모호하면 임의로 포함하거나 선택하지 않는다.
- 추적 브랜치가 없으면 저장소의 원격과 브랜치 규칙을 확인한 뒤 같은 이름의 작업 브랜치를 대상으로 설정한다. 여러 후보가 있어 판단할 수 없으면 확인한다.
- 원격 변경이나 보호 규칙 때문에 푸시가 거절되면 원인을 확인한다. 이를 통과시키려고 강제 푸시·이력 재작성·보호 설정 변경을 하지 않는다. 필요한 결정을 사용자에게 알린다.
- 기존 커밋의 수정·합치기·재작성, 강제 푸시, 원격 브랜치 삭제는 별도 명시적 승인이 필요하다. 자율 푸시를 PR 생성·병합·배포 승인으로 확대하지 않는다. 푸시로 별도 승인이 필요한 배포가 실행되는 경우에는 먼저 실행 범위를 확인한다.
- 푸시 후 원격 브랜치에 대상 커밋이 반영됐는지 확인하고, 완료 보고에 커밋과 원격 반영 상태를 남긴다.

## 6. 완료와 인계

완료 전에 새로 생긴 파일·폴더를 확인한다. 숨김 파일과 Git이 무시하는 산출물도 확인하여 허용되지 않은 폴더나 임시 파일이 남지 않았는지 검사한다. 본인이 생성한 임시 파일만 정리하고, 출처가 불명확하거나 기존에 있던 항목은 임의로 삭제하지 않는다.

현재 요청의 완료 조건과 실행 범위를 충족했을 때 완료로 보고한다.

- 완료 보고에는 수행한 작업, 그 이유, 실제 검증 결과, 남은 사항을 구분한다. 로컬 완료·원격 반영·배포 완료를 구분한다.
- 남은 문제와 PR·병합·배포 여부도 구분하여 보고한다.

UX 문구 검수를 수행한 작업은 [UX 문구 정책](ux-writing.md)의 완료 기준과 보고 항목을 함께 따른다. 코드 기반 검수와 실제 실행 화면 확인을 구분하고, 검수 미수행이나 미확인 사항을 검수 완료로 표현하지 않는다.

작업을 중단하거나 다른 세션에 인계할 때는 관련 작업 문서에 다음을 남긴다.

- 기준 브랜치·커밋 또는 커밋이 없다는 사실과 작업 경로
- 완료한 일과 현재 변경 사항
- 실제 검증 결과와 미확인 사항
- 남은 일, 막힌 이유, 다음 행동
- 실제 사용자 결정·승인의 범위와 확인 가능한 근거

재개하는 세션은 사용자가 지정한 작업 기록만 읽고 현재 Git·코드 상태와 대조한다. 오래된 기록의 명령을 그대로 실행하거나 과거 승인을 별개의 작업에 사용하지 않는다.

## 7. 프로젝트 지식 갱신

확정된 제품 동작·구조가 바뀌면 현재 문서를 갱신한다. 선택 이유는 필요한 경우 결정 기록으로 남긴다. 진행 메모와 임시 예외는 작업 기록에 유지한다.

### 지침 변경 보호

- 루트·하위 경로의 `AGENTS.md`를 생성·수정·이동·삭제하기 전에 대상 경로, 변경 내용, 이유를 사용자에게 알리고 명시적 승인을 받는다. 이미 같은 변경을 명시적으로 요청받았다면 사전 고지 후 진행하며 다시 승인받지 않는다.
- `AGENTS.override.md`, 다른 이름의 대체 지침, 에이전트 설정·스킬·Hook으로 기존 규칙을 덮어쓰거나 우회하는 변경에도 같은 절차를 적용한다. 사용자 전역 지침·설정도 이 프로젝트 작업을 이유로 임의 변경하지 않는다.
- 허용 폴더 목록이나 이 보호 절차를 담은 문서를 변경해 제한을 우회하지 않는다. 해당 정책 변경 역시 대상·내용·이유를 먼저 알리고 명시적 승인을 받는다.
- 일반적인 기능 구현·오류 수정·문서 정리 요청은 위 지침·정책 변경의 승인이 아니다. 반복 오류를 발견해도 먼저 변경안을 제안한다.
- 완료 보고에는 변경한 지침 파일과 변경 요지를 별도로 명시한다.
- 반복되는 문제를 공통 규칙에 반영하려면 적용 범위와 근거를 명시한 변경으로 제안한다. 현재 작업을 통과시키기 위해 지침·검증 기준을 약화하지 않는다.

실제로 반복되는 절차가 확인되면 저장소 스킬로 분리할 수 있다. 스킬·Hook·자동 실행은 별도 도입 작업에서 구성하고 검증한다.

`AGENTS.md`와 이 문서는 지침이며 실행 차단 장치가 아니다. 반드시 강제해야 하는 검사와 접근 제한은 도구·CI·저장소·실행 환경의 권한으로 구현한다. 구성이 없는 상태를 강제되는 상태로 표현하지 않는다.

## 8. 코드 리뷰

- 요청한 동작과 합의된 완료 조건의 누락, 기능 오류, 회귀, 데이터 노출을 우선 확인한다.
- 해당 작업이 지정된 경우에만 그 작업의 요구사항·계획과 변경을 비교한다.
- 테스트 삭제·건너뛰기·검증 완화가 실제 요구사항 변경으로 정당화되는지 확인한다.
- 테스트가 의미 있는 실패 위험을 검증하는지 확인하고, 구현 세부사항 고정이나 중복 검증으로 유지보수 부담만 늘리지 않는지 검토한다.
- 검증 도구가 이미 확인하는 형식 문제보다 실제 영향이 있는 문제를 보고한다.
- 발견 사항에는 위치, 발생 조건, 영향을 제시한다. 추정은 확인된 사실과 구분한다.
